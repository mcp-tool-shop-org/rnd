# Research and Development seat

This repo is the studio's research library: Markdown entries plus a rebuildable
SQLite index, driven by `python -m rnd`. Read README.md for the format.

## Before answering a research question

1. `python -m rnd search <words>` first. The library may already hold it, and
   the NVIDIA skills catalogue is mirrored here too.
2. `python -m rnd readouts <words> [--any]` next: the readouts monorepo holds the
   studio's verified knowledge bases (vocology, training, models, engines, …).
   Tell research agents what it already covers so they target the gaps.
3. `python -m rnd tools` lists the instruments you can use (study-swarm,
   research-os, repo-knowledge, ollama-intern, offrig, engine-room, …) with how
   to invoke each one.

## Filing research

- One entry per topic: `python -m rnd new "<title>" --kind <kind> --field <field>`,
  then fill the sections. Write in your own words; never paste copyrighted text.
- Tag every source with its tier. Pasted AI-search output is `[aggregator]` or
  `[user]`, never `[primary]`; find the primary source if a claim matters.
- Claims start `[unverified]`. Mark `[verified]` only with `(via: …, date)` naming
  what checked it. Verification is proportional (Standing Rule 3): don't run a
  verifier pass by default; check when a claim looks wrong, sources conflict,
  or a decision depends on it.
- Keep "what this is" (Summary, Key points) separate from "what it means for the
  studio" (Studio relevance + `relevance: act | watch | reference`). Research
  from outside the studio's fields is welcome; `reference` is a fine verdict.
- Run `python -m rnd sync --check` and `python -m rnd check` before committing; both exit 1 on errors.
- If a new entry supersedes, contradicts, or supports an older claim by id, run
  `python -m rnd reconcile <entry>` to update the inverse link on the older claim.
- Update as you go with one changelog fragment per update (never bump the version
  or `CHANGELOG.md` in an update PR): `python -m rnd change "<what changed>" [--level nano|micro|patch|minor|major]`.
- `python -m rnd bump`, the version update in `mcptoolshop_rnd/__init__.py` + `CHANGELOG.md`,
  and `git tag -a v<version>` happen **once**, by the R&D seat, in a release PR.
  GitHub releases are only for tool changes (`patch` and up).

## Bench, then shelf

This repo is the bench: the messy counterpart to readouts. Interim, disputed and
wrong results stay visible and honestly marked; don't tidy them away. When a
topic's load-bearing claims are verified, it is promoted into a knowledge base in
readouts-internal, and reaches the public readouts only via the `PUBLIC_KBS`
allow-list in readouts' `shared/export_public.py`. Promotion goes through the
readouts build (study-swarm), never by copying entries across.

## Instruments

A studio tool that research can use gets a file in `instruments/` with
`instrument_status: shipped | planned | retired`, `invoke`, `when` and `where`.

- **Reviewed-diff rule:** instrument files (`instruments/*.md`) are edited **only
  by the R&D seat**, in a reviewed diff whose PR/commit description lists each
  instrument file changed — never by any step or command that summarises outside
  content.

## Hard lines

- Public repo: no home-directory paths, no secrets, and nothing that isn't ours
  to publish. Run the identity scan before pushing.
- **Core dependencies & extras:** `rnd`'s core has no third-party dependencies
  (Python standard library only). Any optional extra lives in an opt-in group, is
  imported lazily, and a command needing a missing extra fails with a named error
  code (`MISSING_EXTRA`) and an install hint.
- `catalogs/*/catalog.json` is generated by `rnd catalog sync`; edit
  `review.json` instead.
- No Ollama Cloud models and no paid verifier seats (Standing Rule 1). Anything
  paid needs the Director's go.
- Tests: `python -m unittest discover -s tests -t .`
