स्टूडियो का अनुसंधान बेंच। किसी भी क्षेत्र से प्राप्त निष्कर्षों को संक्षिप्त
मार्कडाउन प्रविष्टियों के रूप में तेजी से दर्ज किया जाता है, जिसमें प्रत्येक स्रोत को टैग किया जाता है और प्रत्येक दावे को सत्यापित या
असत्यापित के रूप में चिह्नित किया जाता है। प्रयोग उन प्रविष्टियों के बगल में रखे जाते हैं जिनका वे परीक्षण करते हैं। बाहरी कैटलॉग को
दर्शाया और मूल्यांकित किया जाता है, और एक रजिस्ट्री में स्टूडियो के उन उपकरणों की सूची होती है जिनका उपयोग अनुसंधान के लिए किया जा सकता है।
एक कमांड से यह सब खोजा जा सकता है।

## यह कहाँ स्थित है: readouts के सामने बेंच

दो संग्रह स्टूडियो के ज्ञान को संग्रहीत करते हैं, और वे अलग-अलग कार्य करते हैं।

| | अनुसंधान और विकास (यह रिपॉजिटरी) | [readouts](https://github.com/mcp-tool-shop-org/readouts) |
|---|---|---|
| भूमिका | बेंच: जानकारी प्राप्त करना, प्रयोग, खुले प्रश्न | शेल्फ: सत्यापित ज्ञान आधार |
| गति | एक प्रविष्टि कुछ मिनटों में, दावे `unverified` से शुरू होते हैं | अध्ययन समूहों द्वारा निर्मित और सत्यापित |
| आकार | मार्कडाउन प्रविष्टियाँ, प्रत्येक में एक विषय | प्रत्येक डोमेन के लिए एक SQLite ज्ञान आधार |
| कितना अव्यवस्थित | जानबूझकर अव्यवस्थित: विवादित दावे, मृत अंत और अंतरिम परिणाम दृश्यमान रहते हैं | बिल्कुल भी अव्यवस्थित नहीं: प्रत्येक पंक्ति का स्रोत और सत्यापन किया गया है |

ज्ञान एक दिशा में प्रवाहित होता है:

1. **बेंच।** एक खोज परिणाम यहाँ एक प्रविष्टि के रूप में दर्ज होता है। इसके दावे `[unverified]` से शुरू होते हैं,
और केवल `[verified]` के साथ यह दर्शाया जाता है कि इसकी जाँच किसने की।
हमारे अपने उपकरणों पर किए गए माप `rig` स्रोतों के रूप में दर्ज किए जाते हैं, और इनका आधार `experiments/` के अंतर्गत होता है।
2. **आंतरिक शेल्फ।** एक बार जब किसी विषय के भार-वाहक दावों का समर्थन किया जाता है, तो इसे readouts के निजी कार्य भंडार में बनाया जाता है, या इसमें जोड़ा जाता है।
**किसी प्रयोग को समाप्त करना, प्रचार का हिस्सा है** (निदेशक, 2026-10-09)। जब किसी प्रयोग का परिणाम यहाँ दर्ज किया जाता है, तो इसका readouts-internal अद्यतन उसी सत्र में या अगले सत्र में, इसके चार्ट के साथ किया जाता है। बेंच पर कोई भी चीज़ एक सप्ताह से अधिक समय तक नहीं रहती। नियमित छोटे अद्यतन, एक बड़े अद्यतन से बेहतर होते हैं। किसी प्रयोग की README फ़ाइल, इसके परिणाम के अंतर्गत एक पंक्ति में इसके प्रचार को दर्ज करती है:
"प्रचारित: readouts-internal `<kb>` वेव `<n>`, `<date>`", या अभी तक क्यों नहीं।
3. **सार्वजनिक शेल्फ।** एक ज्ञान आधार को सार्वजनिक readouts भंडार में प्रकाशित किया जाता है जब इसे निर्यात अनुमति सूची में जोड़ा जाता है।

`rnd readouts` यहाँ से प्रत्येक readouts ज्ञान आधार की खोज करता है, इसलिए एक सीट दोनों भंडारों तक पहुँचती है। पहले बेंच की खोज करें, फिर शेल्फ की, और फिर अंतर का अध्ययन करें।

यहां किया गया अनुसंधान केवल स्टूडियो के अपने क्षेत्रों तक ही सीमित नहीं है। प्रत्येक प्रविष्टि दो चीजों को अलग-अलग रूप से दर्ज करती है: ज्ञान क्या है, और इसका स्टूडियो के लिए क्या अर्थ है (`relevance: act | watch | reference`)। `reference` एक सटीक निष्कर्ष है।

## इसका उपयोग करें

इसके लिए पायथन 3.10 या उसके बाद का संस्करण और कुछ भी नहीं आवश्यक है (केवल मानक लाइब्रेरी)। यह विंडोज, macOS और लिनक्स पर चलता है। रिपॉजिटरी रूट से:

```bash
python -m rnd search cuda graphs            # full-text over entries + catalogues (stemmed: pair finds pairs)
python -m rnd search --exact PAIR           # whole words, same case: the product, not the word
python -m rnd probe https://github.com/NVIDIA/NeMo-Relay   # licence, release, telemetry hits, already in rnd?
python -m rnd show 2026-10-07-cuda-graphs   # one entry, with backlinks
python -m rnd list --relevance act          # what needs doing
python -m rnd tools                         # instruments this seat can use
python -m rnd readouts splice glitch --any  # search the readouts knowledge bases too
python -m rnd catalog lanes                 # NVIDIA skills by lane, with studio fit
python -m rnd catalog list --fit adjacent   # skills worth using when the need arises
python -m rnd new "Paper title" --kind paper --field audio --tag pitch
python -m rnd check                         # validate every file (exit 1 on errors)
python -m rnd sql "SELECT tier, count(*) FROM sources GROUP BY tier"
python -m rnd bump --note "what changed"  # micro version bump + CHANGELOG section
```

प्रत्येक लिस्टिंग कमांड `--json` एजेंट लेता है। `rnd.cmd` (विंडोज) और
`rnd.sh` (POSIX शेल) पतले रैपर हैं, इसलिए कमांड किसी भी निर्देशिका से काम करता है।

अन्य परियोजनाओं से उपकरण का उपयोग करने के लिए, इसे PyPI से स्थापित करें:

```bash
pip install mcptoolshop-rnd
```

यह `rnd` कमांड स्थापित करता है, लाइब्रेरी नहीं: प्रविष्टियाँ इस रिपॉजिटरी में मौजूद हैं। कमांड लाइब्रेरी को इस क्रम में खोजता है: `--library DIR`, फिर
`$RND_ROOT`, फिर वर्तमान से ऊपर या उसके बराबर निकटतम फ़ोल्डर जिसमें `entries/` और `instruments/` हों। लाइब्रेरी के बाहर, यह `NO_LIBRARY` के साथ समाप्त हो जाता है;
केवल `rnd readouts` इसके बिना काम करता है।

पायथन में, `mcptoolshop_rnd` आयात करें: यह नाम हमेशा काम करता है। `rnd` को संगतता उपनाम के रूप में रखा गया है, लेकिन एक असंबंधित PyPI पैकेज को भी `rnd` कहा जाता है, और यदि दोनों स्थापित हैं, तो यह उपनाम को बदल सकता है। `rnd` कमांड और
`python -m mcptoolshop_rnd` किसी भी तरह से काम करते रहते हैं।

लाइब्रेरी प्रतिदिन बदलती है, इसलिए संस्करणों में पांच खंड होते हैं, `MAJOR.MINOR.PATCH.MICRO.NANO`। पहले तीन खंड `rnd` उपकरण को संस्करण देते हैं; MICRO एक संरचनात्मक लाइब्रेरी परिवर्तन को दर्शाता है और NANO एक सामान्य अद्यतन को। `rnd bump` डिफ़ॉल्ट रूप से अंतिम खंड को बढ़ाता है और अंतिम टैग के बाद से बदले गए फ़ाइलों से एक CHANGELOG अनुभाग लिखता है, इसलिए प्रत्येक अद्यतन को अपना स्वयं का छोटा टैग किया गया संस्करण मिलता है।

निकास कोड: `0` ठीक · `1` अमान्य लाइब्रेरी फ़ाइलें · `2` उपयोग त्रुटि या नहीं मिला ·
`3` रनटाइम विफलता (एक बाहरी उपकरण, या एक अप्रत्याशित त्रुटि)। त्रुटियां एक कोड, एक संदेश और एक संकेत प्रिंट करती हैं; `--debug` ट्रेसबैक जोड़ता है।

## लेआउट

| पथ | क्या | कौन संपादित करता है |
|------|------|-----------|
| `entries/YYYY/*.md` | अनुसंधान प्रविष्टियाँ: सत्य का स्रोत | लोग और एजेंट |
| `experiments/<name>/` | हarness, पिन किए गए इनपुट और रिग माप के लिए परिणाम रसीदें | लोग और एजेंट |
| `experiments/<name>/collect.json` | एक उपकरण रिपॉजिटरी से पिन किए गए कमिट पर एकत्र किए गए रिकॉर्ड (`rnd collect`) | लोग |
| `instruments/*.md` | स्टूडियो उपकरण और प्रोटोकॉल जिनका उपयोग सीट कर सकती है (`kind: instrument`) | लोग और एजेंट |
| `catalogs/<name>/source.json` | कैटलॉग कहां से आता है | लोग |
| `catalogs/<name>/catalog.json` | `rnd catalog sync` से पिन किया गया स्नैपशॉट | उत्पन्न; कभी भी हाथ से संपादित नहीं किया जाता |
| `catalogs/<name>/review.json` | परिवार और आइटम के अनुसार स्टूडियो फिट और नोट्स | लोग |
| `datapacks/<name>/spec.json` | एक डेटा पैक में क्या है: शामिल ग्लोब, लाइसेंस, जनरेटर, होस्ट | लोग |
| `datapacks/<name>/datapack.json` | `rnd datapack build` से मैनिफ़ेस्ट: प्रत्येक फ़ाइल का SHA-256, लाइसेंस, पिन | उत्पन्न; कभी भी हाथ से संपादित नहीं किया जाता |
| `datapacks/<name>/hosted.json` | अपलोड कहां हुआ (रिपॉजिटरी संशोधन) | अपलोड के बाद |
| `mcptoolshop_rnd/` | सीएलआई | कोड |
| `rnd/` | `mcptoolshop_rnd` के लिए संगतता उपनाम | कोड |
| `rnd.db` | SQLite FTS5 इंडेक्स, फ़ाइलों के बदलने पर स्वचालित रूप से पुनर्निर्मित | उत्पन्न; गिट में नहीं |

## प्रविष्टि प्रारूप

```markdown
---
id: 2026-10-07-cuda-graphs        # defaults to the file name
title: CUDA Graphs
date: 2026-10-07
kind: concept                     # finding concept release paper tool catalog rig-fact event question decision instrument
relevance: reference              # act | watch | reference
fields: [gpu-computing]           # any research field, open vocabulary
tags: [cuda-graphs, pytorch]
---

## Summary
## Key points
## Studio relevance
## Claims
- [unverified] A checkable statement.
- [verified] A checked statement. (via: what checked it, date)
## Sources
- [primary] https://… — publisher
```

- **स्रोत स्तर:** `primary` (विक्रेता दस्तावेज़, पेपर, रिपॉजिटरी), `secondary`
(विश्वसनीय लेख), `aggregator` (सारांश साइटें, एआई खोज आउटपुट),
`user` (किसी व्यक्ति द्वारा प्रदान किया गया: स्लाइड, नोट्स), `rig` (हमारे उपकरणों पर मापा गया)।
- **दावे का आत्मविश्वास:** `unverified`, `verified`, `disputed`, `wrong`। एक
`verified` या `wrong` दावे में यह बताना चाहिए कि `(via: …)` के साथ इसे किसने सत्यापित किया।
- `[[entry-id]]` प्रविष्टियों को जोड़ता है; `rnd show` बैकलिंक सूचीबद्ध करता है।

## डेटा पैक

बहुत बड़ा या बहुत अधिक डेटा जो क्लोन के लिए उपयुक्त नहीं है, उसे **डेटा पैक** के रूप में पेश किया जाता है: बाइट्स एक हगिंग फेस डेटासेट रिपॉजिटरी (प्रकाशित होने तक निजी) पर मौजूद हैं, और लाइब्रेरी केवल एक छोटा मैनिफ़ेस्ट रखती है। अखंडता मॉडल [research-packs](https://github.com/mcp-tool-shop-org/research-packs) से आता है: एक मैनिफ़ेस्ट, प्रत्येक फ़ाइल के लिए एक SHA-256, एक कमांड में सत्यापन, और एक सूची।

```bash
rnd datapack build natural-errors --source experiments/natural-errors  # reads datapacks/natural-errors/spec.json
rnd datapack list
hf download mcp-tool-shop/rnd-natural-errors --repo-type dataset --local-dir ne
rnd datapack verify natural-errors --copy ne/files                      # PASS when every byte matches
```

- **प्रत्येक फ़ाइल को विनिर्देश में एक लाइसेंस की आवश्यकता होती है।** मॉडल आउटपुट अपने मॉडल की शर्तों को ले जाते हैं (उदाहरण के लिए, Llama 3.1 आउटपुट के लिए "Llama के साथ निर्मित")। `rnd datapack build` एक ऐसे पैकेज को अस्वीकार करता है जो किसी फ़ाइल को असुरक्षित छोड़ देता है।
- **प्रत्येक जनरेटिंग मॉडल को पिन किया जाता है** (Ollama डाइजेस्ट, HF संशोधन या API मॉडल आईडी), और इसकी भूमिका भी।
- **`rnd check` प्रत्येक मेनिफेस्ट को मान्य करता है** और एक ऐसे मेनिफेस्ट पर विफल हो जाता है जिसे हाथ से संपादित किया गया हो।
- अपलोड फ़ाइलों के साथ `datapack.json` ले जाता है, इसलिए कोई भी इस भंडार के बिना सत्यापित कर सकता है: `pip install mcptoolshop-rnd`।

## एकत्रित किए गए प्रयोग रिकॉर्ड

एक उपकरण भंडार अपने स्वयं के पूर्व-पंजीकृत विनिर्देशों और रन रिकॉर्ड (interlock की रसीदें) को प्रतिबद्ध करता है, उसी तरह जैसे प्रत्येक भंडार अपने एटलस मानचित्र को प्रतिबद्ध करता है। पुस्तकालय केवल संख्याओं की एक संक्षिप्त प्रति प्रकाशित करता है, जिसे `rnd collect` द्वारा उपकरण भंडार में पिन किए गए कमिट से बनाया जाता है:

```bash
rnd collect                 # list the experiments that collect records
rnd collect e4b             # read each source with git show, trim it, write experiments/e4b/results/
rnd collect e4b --check     # recompute every output; exit 1 if any differs from the committed file
```

- **`experiments/<name>/collect.json`** रिपॉजिटरी, उस संबंधित क्लोन का नाम देता है जिससे इसे पढ़ा गया है (`--clone` इसे ओवरराइड करता है), और प्रत्येक स्रोत: इसका पथ, कमिट, इसके बाइट्स का SHA-256, आउटपुट और प्रयोग के `extract.py` में ट्रिम फ़ंक्शन।
- **एक पिन किया गया स्रोत कभी नहीं बदलता।** वे बाइट्स जो अब पिन से मेल नहीं खाते हैं, उन्हें अस्वीकार कर दिया जाता है।
- **प्रत्येक रिकॉर्ड में उत्पत्ति शामिल होती है:** रिपॉजिटरी, स्रोत पथ और ट्रिम किए गए बाइट्स का SHA-256।
- **प्रत्येक आउटपुट को लिखने से पहले सार्वजनिक रूप से सुरक्षित किया जाता है।** कोई भी मशीन पथ, होम निर्देशिका या पर्यावरण फ़ील्ड नहीं रहता है, और एक प्रयोग का मॉड्यूल एक सख्त सुरक्षा जोड़ सकता है। किसी भी अस्वीकृति पर कुछ भी नहीं लिखा जाता है।

## परीक्षण से पहले एक टूल का परीक्षण

`rnd probe <url> …` प्रत्येक स्रोत के अपने API से एक टूल या मॉडल के बारे में पहले प्रश्नों का उत्तर देता है, न कि किसी वेब पेज के सारांश से:

- **GitHub** (`gh api` के माध्यम से, इसलिए यह आपके GitHub CLI लॉगिन का उपयोग करता है): लाइसेंस, चाहे वह संग्रहीत हो, अंतिम पुश, नवीनतम रिलीज़, और "टेलीमेट्री" के लिए एक कोड खोज। एक हिट पढ़ने के लिए एक सुराग है, कभी भी प्रमाण नहीं; शून्य हिट भी प्रमाण नहीं है।
- **हगिंग फेस:** लाइसेंस टैग, या "अन्य" के लिए कार्ड का लाइसेंस नाम और लिंक; गेटिंग; अंतिम परिवर्तन।
- **PyPI और npm:** लाइसेंस, नवीनतम संस्करण और यह कब प्रकाशित किया गया था।
- **rnd स्वयं:** नाम के लिए एक सटीक-शब्द खोज, ताकि आप जान सकें कि क्या लाइब्रेरी में यह पहले से मौजूद है।

एक ऐसा स्रोत जिसे एक्सेस नहीं किया जा सकता है, उसे अज्ञात के रूप में रिपोर्ट किया जाता है, साथ में इसका कारण भी।

## स्रोत की निगरानी

`rnd watch` [docs/watchlist.json](docs/watchlist.json) में स्रोतों की जांच करता है और अंतिम जांच के बाद से क्या नया है, इसकी रिपोर्ट करता है:

- NVIDIA का तकनीकी ब्लॉग;
- CUDA टूलकिट संस्करण;
- NVIDIA के नए हगिंग फेस मॉडल;
- NVIDIA कैटलॉग कौशल;
- स्टूडियो द्वारा चलाए जा रहे इंजनों और उपकरणों की रिलीज़, जैसे Ollama, OpenVINO, PyTorch, ComfyUI और क्लाउड कोड।

```bash
python -m rnd watch                  # what's new; records what it saw
python -m rnd watch --no-save --json # look without recording
python -m rnd watch --only ollama    # one source
```

जो कुछ भी इसने देखा है, उसे रिपॉजिटरी के बाहर एक राज्य फ़ाइल में रखा जाता है (`$RND_WATCH_STATE`, अन्यथा `~/.rnd/watch-state.json`)। किसी स्रोत की पहली जांच एक आधार रेखा है: यह वर्तमान वस्तुओं को रिकॉर्ड करता है और किसी भी नई वस्तु की रिपोर्ट नहीं करता है। एक प्री-रिलीज़ को कभी भी स्रोत के नवीनतम संस्करण के रूप में रिपोर्ट नहीं किया जाता है; इसके बजाय, एक नया संस्करण इसके बगल में दिखाया जाता है। GitHub रिलीज़ नोट्स और कमिट संदेश JSON आउटपुट में रखे जाते हैं, ताकि पाठक को प्रत्येक पृष्ठ को प्राप्त करने की आवश्यकता न हो। एक ऐसा स्रोत जिसे एक्सेस नहीं किया जा सकता है, उसे अज्ञात के रूप में रिपोर्ट किया जाता है, और इसकी स्थिति को अपरिवर्तित छोड़ दिया जाता है ताकि चुपचाप कुछ भी छोड़ न दिया जाए।

कमांड एक साप्ताहिक अनुष्ठान का नियतात्मक आधा भाग है (निर्देशक, 2026-10-13)। एक स्काउट नई वस्तुओं को पढ़ता है, किसी भी उम्मीदवार टूल का `rnd probe` के साथ परीक्षण करता है, लाइब्रेरी को `rnd search --exact` के साथ जांचता है, और एक संक्षिप्त रैंक वाली रिपोर्ट लिखता है: क्या फ़ाइल करना है, क्या प्रयास करना है, और क्या छोड़ना है। पुल अनुरोध द्वारा एक स्रोत जोड़ें, और बताएं कि यह क्यों महत्वपूर्ण है।

## अन्य स्टूडियो टूल से संबंध

- **readouts** वह सत्यापित शेल्फ है जिससे यह बेंच जुड़ा है (ऊपर देखें)।
- **research-os** किसी एक विषय के लिए एक गेटेड, जमे हुए साक्ष्य पैकेज बनाता है। एक ऐसा विषय जिस पर किसी निर्णय पर निर्भर किया जाता है, वह research-os पैकेज में विकसित हो सकता है, जो प्रविष्टि से जुड़ा होता है।
- **repo-knowledge** स्टूडियो के अपने भंडारों को अनुक्रमित करता है; यह पुस्तकालय उनके बाहर के ज्ञान को कवर करता है।
- कुछ डिज़ाइन करते समय एकत्र किए गए निष्कर्ष भी यहाँ हैं, ताकि वे उस सत्र से आगे भी बने रहें जिसने उन्हें उत्पन्न किया।

पूर्ण उपकरण रजिस्ट्री के लिए `python -m rnd tools` देखें, और स्टूडियो के वर्कफ़्लो मानकों के विरुद्ध वर्कफ़्लो कैसे स्कोर करता है, इसके लिए [docs/standards.md](docs/standards.md) देखें।
