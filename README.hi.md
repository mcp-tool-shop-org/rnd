स्टूडियो का अनुसंधान बेंच। किसी भी क्षेत्र से प्राप्त निष्कर्षों को संक्षिप्त
मार्कडाउन प्रविष्टियों के रूप में तेजी से प्रस्तुत किया जाता है, जिसमें प्रत्येक स्रोत को टैग किया जाता है और प्रत्येक दावे को जांचा गया या
नहीं के रूप में चिह्नित किया जाता है। प्रयोग उन प्रविष्टियों के बगल में होते हैं जिनका वे परीक्षण करते हैं। बाहरी कैटलॉग को
दर्शाया और मूल्यांकित किया जाता है, और एक रजिस्ट्री में स्टूडियो के उन उपकरणों की सूची होती है जिनका अनुसंधान उपयोग कर सकता है।
एक कमांड से यह सब खोजा जा सकता है।

## यह कहाँ स्थित है: readouts के सामने बेंच

दो भंडार स्टूडियो के ज्ञान को संग्रहीत करते हैं, और वे अलग-अलग कार्य करते हैं।

| | अनुसंधान और विकास (यह रिपॉजिटरी) | [readouts](https://github.com/mcp-tool-shop-org/readouts) |
|---|---|---|
| भूमिका | बेंच: जानकारी प्राप्त करना, प्रयोग, खुले प्रश्न | शेल्फ: सत्यापित ज्ञान आधार |
| गति | एक प्रविष्टि मिनटों में, दावे `unverified` से शुरू होते हैं | अध्ययन समूहों द्वारा निर्मित और जांचा गया |
| आकार | मार्कडाउन प्रविष्टियाँ, प्रत्येक में एक विषय | प्रत्येक डोमेन के लिए एक SQLite ज्ञान आधार |
| कितना अव्यवस्थित | जानबूझकर अव्यवस्थित: विवादित दावे, मृत अंत और अस्थायी परिणाम दृश्यमान रहते हैं | बिल्कुल भी अव्यवस्थित नहीं: प्रत्येक पंक्ति का स्रोत और सत्यापन किया गया है |

ज्ञान एक दिशा में बढ़ता है:

1. **बेंच।** एक निष्कर्ष यहां एक प्रविष्टि के रूप में आता है। इसके दावे `[unverified]` से शुरू होते हैं, और उन्हें `[verified]` केवल इस नोट के साथ चिह्नित किया जाता है कि किस चीज़ ने उनकी जाँच की। हमारी अपनी मशीनों पर किए गए माप `rig` स्रोतों के रूप में दर्ज किए जाते हैं, और उनका हार्नेस `experiments/` के अंतर्गत होता है।
2. **आंतरिक शेल्फ।** एक बार जब किसी विषय के महत्वपूर्ण दावों का समर्थन किया जाता है, तो इसे
readouts के निजी कार्य रिपॉजिटरी में एक ज्ञान आधार के रूप में बनाया जाता है, या इसमें जोड़ा जाता है।
**प्रमोशन (ज्ञान आधार में आगे बढ़ाना) किसी प्रयोग को समाप्त करने का हिस्सा है** (निदेशक, 2026-10-09)। जब
किसी प्रयोग का परिणाम यहां दर्ज किया जाता है, तो इसका readouts-internal अपडेट उसी सत्र में या अगले सत्र में, इसके चार्ट के साथ होता है। बेंच पर एक सप्ताह से अधिक समय तक कुछ भी नहीं रहता है। नियमित छोटे अपडेट, एक बड़े अपडेट से बेहतर होते हैं। किसी प्रयोग के README में इसके प्रचार को इसके परिणाम के नीचे एक पंक्ति के रूप में दर्ज किया जाता है:
"प्रचारित: readouts-internal `<kb>` वेव `<n>`, `<date>`", या यदि अभी तक नहीं, तो इसका कारण।
3. **सार्वजनिक शेल्फ।** जब किसी ज्ञान आधार को निर्यात अनुमति सूची में जोड़ा जाता है, तो इसे सार्वजनिक readouts रिपॉजिटरी में प्रकाशित किया जाता है।

`rnd readouts` यहां से प्रत्येक readouts ज्ञान आधार को खोजता है, इसलिए एक सीट दोनों भंडारों तक पहुंचती है। पहले बेंच को खोजें, फिर शेल्फ को, और फिर अंतर का अनुसंधान करें।

यहां किया गया अनुसंधान केवल स्टूडियो के अपने क्षेत्रों तक ही सीमित नहीं है। प्रत्येक प्रविष्टि दो चीजों को अलग-अलग रूप से दर्ज करती है: ज्ञान क्या है, और इसका स्टूडियो के लिए क्या अर्थ है (`relevance: act | watch | reference`)। `reference` एक अच्छा निष्कर्ष है।

## इसका उपयोग करें

इसके लिए पायथन 3.10 या उसके बाद का संस्करण और कुछ भी नहीं (केवल मानक लाइब्रेरी) की आवश्यकता होती है। यह विंडोज, macOS और लिनक्स पर चलता है। रिपॉजिटरी की रूट निर्देशिका से:

```bash
python -m rnd search cuda graphs            # full-text over entries + catalogues (stemmed: pair finds pairs)
python -m rnd search --exact PAIR           # whole words, same case: the product, not the word
python -m rnd probe https://github.com/NVIDIA/NeMo-Relay   # licence, release, telemetry hits, already in rnd?
python -m rnd show 2026-10-07-cuda-graphs   # one entry, with backlinks
python -m rnd list --relevance act          # what needs doing
python -m rnd tools                         # instruments this seat can use
python -m rnd readouts splice glitch --any  # search the readouts knowledge bases too
python -m rnd catalog lanes                 # NVIDIA skills by lane, with studio fit
python -m rnd catalog list --fit adjacent   # skills worth using when the need arises
python -m rnd new "Paper title" --kind paper --field audio --tag pitch
python -m rnd new-question "Why does X happen?" --field audio
python -m rnd sync --check                  # verify numbers bound to experiments/<id>/results.json
python -m rnd check                         # validate every file (exit 1 on errors)
python -m rnd similar 2026-10-07-cuda-graphs --limit 3  # closest claims in other entries (read-only)
python -m rnd digest --since v1.1.24.0.14   # entries, claims and questions changed since a tag or date
python -m rnd sql "SELECT tier, count(*) FROM sources GROUP BY tier"
python -m rnd change "what changed"         # add a changelog fragment under changes/ (nano by default)
python -m rnd bump --note "release note"    # release PR: apply changes/ fragments, bump version + CHANGELOG
```

प्रत्येक लिस्टिंग कमांड एजेंटों के लिए `--json` स्वीकार करता है। `rnd.cmd` (विंडोज) और
`rnd.sh` (POSIX शेल) पतले रैपर हैं, इसलिए कमांड किसी भी निर्देशिका से काम करता है।

अन्य परियोजनाओं से उपकरण का उपयोग करने के लिए, इसे PyPI से स्थापित करें:

```bash
pip install mcptoolshop-rnd
```

यह `rnd` कमांड स्थापित करता है, लाइब्रेरी नहीं: प्रविष्टियाँ इस रिपॉजिटरी में मौजूद हैं। कमांड इस क्रम में एक लाइब्रेरी ढूंढता है: `--library DIR`, फिर
`$RND_ROOT`, फिर वर्तमान निर्देशिका से ऊपर या उसके बराबर निकटतम फ़ोल्डर जिसमें `entries/` और `instruments/` हों। लाइब्रेरी के बाहर, यह `NO_LIBRARY` के साथ बंद हो जाता है;
केवल `rnd readouts` इसके बिना काम करता है।

पायथन में, `mcptoolshop_rnd` आयात करें: यह नाम हमेशा काम करता है। `rnd` को संगतता उपनाम के रूप में रखा गया है, लेकिन एक असंबंधित PyPI पैकेज को भी `rnd` कहा जाता है, और यदि दोनों स्थापित हैं, तो यह उपनाम को बदल सकता है। `rnd` कमांड और
`python -m mcptoolshop_rnd` किसी भी तरह से काम करते रहते हैं।

लाइब्रेरी प्रतिदिन बदलती है, इसलिए संस्करणों में पांच खंड होते हैं, `MAJOR.MINOR.PATCH.MICRO.NANO`। पहले तीन खंड `rnd` उपकरण को संस्करण देते हैं; MICRO एक संरचनात्मक लाइब्रेरी परिवर्तन को दर्शाता है और NANO एक सामान्य अपडेट को। सामान्य अपडेट `rnd change` के माध्यम से `changes/` के तहत एक परिवर्तन लॉग खंड जोड़ते हैं; रिलीज के समय, `rnd bump` सभी खंडों का उपभोग करता है, उच्चतम खंड स्तर द्वारा संस्करण को एक बार आगे बढ़ाता है, और एक CHANGELOG अनुभाग लिखता है।

निकास कोड: `0` ठीक · `1` अमान्य लाइब्रेरी फ़ाइलें · `2` उपयोग त्रुटि या नहीं मिला ·
`3` रनटाइम विफलता (एक बाहरी उपकरण, या एक अप्रत्याशित त्रुटि)। त्रुटियां एक कोड, एक संदेश और एक संकेत प्रिंट करती हैं; `--debug` ट्रेसबैक जोड़ता है।

## लेआउट

| पथ | क्या | कौन संपादित करता है |

| `questions/*.md` | खुले और उत्तरित अनुसंधान प्रश्न | लोग और एजेंट |
| `changes/*.md` | अप्रकाशित परिवर्तन लॉग खंड (`rnd change`) | लोग और एजेंट (`rnd bump` उपभोग करता है) |
| `experiments/<name>/` | हर्नेसेस, पिन किए गए इनपुट, `results.json`, और परिणाम रसीदें | लोग और एजेंट |
| `experiments/<name>/collect.json` | एक उपकरण रिपॉजिटरी से पिन किए गए कमिट पर एकत्र किए गए रिकॉर्ड (`rnd collect`) | लोग |
| `instruments/*.md` | स्टूडियो उपकरण और प्रोटोकॉल जिनका उपयोग सीट कर सकती है (`kind: instrument`) | केवल अनुसंधान और विकास सीट (समीक्षित अंतर) |
| `catalogs/<name>/source.json` | कैटलॉग कहां से आता है | लोग |
| `catalogs/<name>/catalog.json` | `rnd catalog sync` से पिन किया गया स्नैपशॉट | उत्पन्न; कभी भी हाथ से संपादित नहीं किया जाता |
| `catalogs/<name>/review.json` | स्टूडियो फिट और प्रत्येक परिवार और आइटम के लिए नोट्स | लोग |
| `datapacks/<name>/spec.json` | एक डेटा पैक में क्या है: शामिल ग्लोब्स, लाइसेंस, जनरेटर, होस्ट | लोग |
| `datapacks/<name>/datapack.json` | `rnd datapack build` से मेनिफेस्ट: प्रत्येक फ़ाइल का SHA-256, लाइसेंस, पिन | उत्पन्न; कभी भी हाथ से संपादित नहीं किया जाता |
| `datapacks/<name>/hosted.json` | अपलोड कहां हुआ (रिपॉजिटरी संशोधन) | अपलोड के बाद |
| `mcptoolshop_rnd/` | सीएलआई | कोड |
| `rnd/` | `mcptoolshop_rnd` के लिए संगतता उपनाम | कोड |
| `rnd.db` | SQLite FTS5 इंडेक्स, जब फ़ाइलें बदलती हैं तो स्वचालित रूप से पुनर्निर्मित | उत्पन्न; गिट में नहीं |
| `rnd.misses.jsonl` | `rnd.db` के बगल में स्थानीय शून्य-हिट खोज लॉग (`RND_NO_USAGE=1` अक्षम करता है) | उत्पन्न; गिट में नहीं |

## प्रविष्टि प्रारूप

```markdown
---
id: 2026-10-07-cuda-graphs        # defaults to the file name
title: CUDA Graphs
date: 2026-10-07
kind: concept                     # finding concept release paper tool catalog rig-fact event question decision instrument
relevance: reference              # act | watch | reference
fields: [gpu-computing]           # any research field, open vocabulary
tags: [cuda-graphs, pytorch]
---

## Summary
## Key points
## Studio relevance
## Claims
- [unverified] A checkable statement.
- [verified] [c-a1b2c3d4] A checked statement. (via: what checked it, date)
## Sources
- [primary] https://… — publisher
```

- **स्रोत स्तर:** `primary` (विक्रेता दस्तावेज़, पेपर, रिपॉजिटरी), `secondary`
(विश्वसनीय लेख), `aggregator` (सारांश साइटें, एआई खोज आउटपुट),
`user` (किसी व्यक्ति द्वारा प्रदान किया गया: स्लाइड, नोट्स), `rig` (हमारे मशीनों पर मापा गया)।
- **दावे का आत्मविश्वास:** `unverified`, `verified`, `disputed`, `wrong`,
`superseded`। `verified` या `wrong` दावे को यह बताना चाहिए कि `(via: …)` के साथ इसकी जांच किसने की।
- `[[entry-id]]` प्रविष्टियों को जोड़ता है; `rnd show` बैकलिंक सूचीबद्ध करता है।

## परिवर्तन लॉग खंड

अपडेट `mcptoolshop_rnd/__init__.py` या `CHANGELOG.md` को सीधे संपादित नहीं करते हैं, इसलिए
समानांतर शाखाएँ संस्करण पंक्ति पर कभी भी टकराती नहीं हैं:

```bash
python -m rnd change "Add study of XYZ"                # writes changes/YYYY-MM-DD-<hex>-<slug>.md (level: nano)
python -m rnd change "New tool feature" --level minor  # levels: nano | micro | patch | minor | major
python -m rnd bump --dry-run                           # preview version bump from changes/ fragments
python -m rnd bump                                     # release PR: bump once, update CHANGELOG.md, delete fragments
```

`changes/` के अंतर्गत कोई फ़ाइलें नहीं होने पर, `rnd bump [nano|micro|…] [--note …]` अपनी
git-diff व्यवहार को बनाए रखता है। `__init__.py` और `CHANGELOG.md` दोनों को अस्थायी फ़ाइलों के माध्यम से स्टेज किया जाता है और `os.replace` के साथ बदला जाता है, यदि
CHANGELOG स्वैप विफल रहता है तो `__init__.py` को वापस किया जाता है। यदि किसी त्रुटि के कारण `__init__.py`, `CHANGELOG.md` से आगे निकल जाता है,
तो मिलान स्तर पर फिर से चलाने से बम्प पूरा हो जाता है और कोई अन्य स्तर `BAD_CHANGELOG` के साथ अस्वीकार कर देता है। एक अंतर बना रहता है: दोनों फ़ाइलों के बदले जाने के बाद लेकिन `changes/` के अंतर्गत टुकड़ों के हटाए जाने से पहले यदि क्रैश हो जाए, तो वे अपनी जगह पर बने रहते हैं, और फिर से चलाने पर दूसरी बार बम्प होगा, इसलिए पहले उन टुकड़ों को हाथ से हटा दें। `rnd check` किसी भी
गलत स्वरूपित टुकड़े को त्रुटि के रूप में रिपोर्ट करता है।

## बाउंड संख्याएँ

एक प्रयोग सार्वजनिक रूप से सुरक्षित सारांश संख्याओं को `experiments/<id>/results.json` में रख सकता है और प्रविष्टियों, संक्षिप्त विवरण या
प्रयोग नोट्स में संख्याओं को सीधे शाब्दिक के बाद बाइंड कर सकता है:

```markdown
The judge scored 84.2%<!-- rnd:experiments/e4b/results.json#accuracy:.1% --> on the held-out split.
```

- रॉ मार्कडाउन, `grep` और SQLite इंडेक्स सादे शाब्दिक (`84.2%`) को बनाए रखते हैं;
GitHub और स्टार्लाइट `84.2%` को किसी दृश्यमान मार्कर या लिंक के बिना प्रस्तुत करते हैं।
- `rnd sync [paths…]`, `results.json` से बाउंड शाब्दिकों को पायथन प्रारूप विनिर्देश का उपयोग करके फिर से लिखता है; `rnd sync --check`, यदि कोई भी
शाब्दिक भिन्न है तो बिना कुछ लिखे निकास कोड `1` के साथ समाप्त हो जाता है।
- `rnd check` किसी भी असंगत बाउंड शाब्दिक, गुम फ़ाइल या गुम कुंजी को त्रुटि मानता है, और उन `[verified]` दावों पर चेतावनी देता है जिनका `(via: …)` किसी रेपो
प्रयोग का नाम लेता है जबकि उनमें अभी भी अनबाउंड संख्याएँ हैं — उन सादे पूर्णांकों (बिना दशमलव बिंदु, प्रतिशत चिह्न, हजार विभाजक या अंतिम इकाई के) को अनदेखा करते हुए जो प्रविष्टि के अपने शीर्षक या टैग में ठीक पहले आने वाले शब्द के साथ जोड़ी बनाते हैं या `RTX` या `GTX` (3–4 अंक) या `CUDA`, `PTX`, `Gemma`, `Llama`, `Qwen`,
`Claude`, `GPT` या `Phi` (1–2 अंक) के बाद आते हैं।

## दावे आईडी और लिंक

दावे स्थिर, नियतात्मक `c-<hex>` आईडी और आईडी द्वारा पुराने दावों के साथ स्पष्ट संबंध (`supersedes`, `contradicts`, `supports`) रख सकते हैं:

```bash
python -m rnd claims                               # list indexed claims (--state superseded, --json)
python -m rnd claims assign <entry>                # add deterministic c-<hex> ids to one entry's claims
python -m rnd similar <entry> [--limit 5]          # closest claims in other entries (read-only)
python -m rnd reconcile <entry>                    # mark older claims (superseded / disputed / supported-by)
```

`rnd similar <entry>`, अन्य प्रविष्टियों के विरुद्ध `<entry>` के प्रत्येक दावे के लिए `claims_fts` पर एक रीड-ओनली SQLite FTS5 BM25 क्वेरी चलाता है (`--limit` डिफ़ॉल्ट रूप से 5 है),
`superseded` या `disputed` हिट को उन दावों के साथ चिह्नित करता है जिन्होंने उन्हें प्रतिस्थापित या खंडित किया,
सटीक `(supersedes: id)` / `(contradicts: id)` / `(supports: id)`
खंडों और `rnd reconcile <entry>` कमांड को प्रिंट करता है, और कभी भी `rnd.db` या किसी भी
प्रविष्टि को नहीं लिखता है। `rnd reconcile <entry>` केवल आईडी (यदि गुम है), अद्यतन स्थिति और
उलटा संबंध (`superseded-by`, `contradicted-by`, `supported-by`) को पुराने दावे की पंक्ति में उसकी अपनी फ़ाइल में लिखता है, बिना उसके वाक्य या किसी अन्य
पंक्ति को छुए (एक `[wrong]` दावे को `[wrong]` छोड़ देता है जब खंडित किया जाता है)। `rnd claims assign` और `rnd reconcile` दोनों अस्वीकार करते हैं (`MULTIPLE_CLAIMS_HEADINGS`)
बिना लिखे यदि किसी प्रविष्टि में एक से अधिक वास्तविक `## Claims` हेडिंग है।
`rnd check` टूटे हुए लक्ष्य आईडी, एकतरफा लिंक (`rnd reconcile` चलाने या खंड को हटाने और `superseded` या `disputed`
स्थिति को रीसेट करने का संकेत देने) या एक अधूरे कोड बाड़ पर त्रुटि देता है,
और `[superseded]` दावे पर कोई `(superseded-by: …)` लिंक न होने पर चेतावनी देता है।
`rnd search` और `rnd show` `superseded` और `disputed` दावों को चिह्नित करते हैं और उस दावे का नाम बताते हैं जिसने उन्हें प्रतिस्थापित या खंडित किया।

## क्या बदला (सारांश)

`rnd digest --since <git ref or YYYY-MM-DD> [--json]`, पहले के कमिट पर लाइब्रेरी की तुलना करता है (मेमोरी में गिट ऑब्जेक्ट से पार्स किया गया, बिना वर्किंग
ट्री, गिट इंडेक्स, `rnd.db` या अस्थायी फ़ाइलों को छुए) वर्तमान ट्री के साथ:

```bash
python -m rnd digest --since v1.1.24.0.14
python -m rnd digest --since 2026-11-19 --json
```

यह जोड़ी गई प्रविष्टियों, जोड़े गए दावों, हटाए गए दावों, दावे की स्थिति में बदलाव (`old_state -> new_state`, उन चीज़ों के साथ जिन्होंने उन्हें प्रतिस्थापित या खंडित किया), और
खुले, उत्तर दिए गए (उत्तर देने वाले दावे आईडी के साथ) और पार्क किए गए प्रश्नों की रिपोर्ट करता है, साथ ही
गिनती भी। `YYYY-MM-DD` तिथि वर्तमान शाखा की पहली-पैरेंट पंक्ति के साथ नवीनतम कमिट पर हल हो जाती है (`HEAD`) जिसकी कमिटर तिथि उस दिन या उससे पहले है। दावे `id` द्वारा मेल खाते हैं जब दोनों पक्षों में एक होता है, अन्यथा `(entry, exact text)` द्वारा, इसलिए बिना आईडी वाला कोई पुनः वाक्यांशित दावा एक हटाए गए दावे और एक जोड़े गए दावे के रूप में दिखाई देता है, कभी भी स्थिति परिवर्तन के रूप में नहीं।

## खुले प्रश्न

खुले प्रश्न `questions/` के अंतर्गत व्यक्तिगत मार्कडाउन फ़ाइलों के रूप में रहते हैं, जिनकी स्थिति `open`, `investigating`, `answered` या `parked` है:

```bash
python -m rnd new-question "Does X hold on Y?" --field systems
python -m rnd questions --status open --json
```

जब किसी प्रश्न का `status` `answered` होता है, तो उसके फ्रंटमैटर `answered_by` सूची में कम से कम एक मौजूदा दावे आईडी का नाम होना चाहिए; `rnd check` एक मौजूदा दावे आईडी के बिना `answered` प्रश्न को त्रुटि के रूप में मानता है। प्रश्नों को `rnd.db` में अनुक्रमित किया जाता है और `rnd search` और `rnd show` द्वारा लौटाया जाता है।

## स्थानीय खोज-मिस लॉग

जब `rnd search` कोई मिलान नहीं लौटाता है, तो यह एक JSON पंक्ति (`time` और
`query`) को `rnd.db` के बगल में एक स्थानीय `.misses.jsonl` फ़ाइल में जोड़ता है (`rnd.misses.jsonl` रेपो रूट में, गिट-अनदेखा; या `<stem>.misses.jsonl` `--db` / `RND_DB` के बगल में,
इसलिए `--db foo.db` इसके बगल में `foo.misses.jsonl` लिखता है, न कि `foo.db.misses.jsonl`)।
कुछ और रिकॉर्ड नहीं किया जाता है, कुछ भी नेटवर्क पर नहीं भेजा जाता है, `RND_NO_USAGE=1`
लॉगिंग को बंद कर देता है, और फ़ाइल को हटाने से यह पूरी तरह से हट जाती है।
`rnd stats --usage` कुल मिस गणना और सबसे अधिक बार खोए गए प्रश्नों को प्रिंट करता है।

## उपकरण फ़ाइलें और वैकल्पिक अतिरिक्त

- **उपकरण फ़ाइलें (`instruments/*.md`):** केवल आर एंड डी सीट द्वारा एक समीक्षा किए गए अंतर में संपादित की जाती हैं, जिसके विवरण में प्रत्येक बदली गई उपकरण फ़ाइल सूचीबद्ध होती है, कभी भी किसी ऐसे चरण या कमांड द्वारा नहीं जो बाहरी सामग्री का सारांश देता है (`rnd watch`, `rnd probe`,
`rnd collect`, `rnd catalog sync`)।
- **मुख्य निर्भरताएँ और अतिरिक्त:** `rnd` का मुख्य भाग केवल पायथन मानक लाइब्रेरी है। कोई भी वैकल्पिक अतिरिक्त एक ऑप्ट-इन समूह में रहता है और आलसी रूप से आयात किया जाता है; एक कमांड जिसे किसी गुम अतिरिक्त की आवश्यकता होती है, वह `MISSING_EXTRA` और एक इंस्टॉलेशन संकेत के साथ विफल हो जाता है।

## डेटा पैक

क्लोन के लिए बहुत बड़ी या बहुत भारी संसाधित डेटा को **डेटा पैक** के रूप में पेश किया जाता है: बाइट्स एक हगिंग फेस डेटासेट रेपो (प्रकाशित होने तक निजी) पर रहते हैं, और लाइब्रेरी केवल एक छोटा
मैनिफेस्ट रखती है। अखंडता मॉडल [research-packs](https://github.com/mcp-tool-shop-org/research-packs) से आता है: एक मैनिफेस्ट, प्रत्येक फ़ाइल के लिए एक SHA-256, एक-कमांड सत्यापन, और एक सूची।

```bash
rnd datapack build natural-errors --source experiments/natural-errors  # reads datapacks/natural-errors/spec.json
rnd datapack list
hf download mcp-tool-shop/rnd-natural-errors --repo-type dataset --local-dir ne
rnd datapack verify natural-errors --copy ne/files                      # PASS when every byte matches
```

- **प्रत्येक फ़ाइल को विनिर्देश में एक लाइसेंस की आवश्यकता होती है।** मॉडल आउटपुट अपने मॉडल की शर्तों को वहन करते हैं (उदाहरण के लिए Llama 3.1 आउटपुट के लिए "Built with Llama")। `rnd datapack build` एक ऐसे पैक को अस्वीकार करता है जो किसी फ़ाइल को बिना कवर के छोड़ देता है।
- **प्रत्येक जनरेटिंग मॉडल को पिन किया जाता है** (Ollama डाइजेस्ट, एचएफ संशोधन या एपीआई मॉडल आईडी), इसकी भूमिका के साथ।
- **`rnd check` प्रत्येक मैनिफेस्ट को मान्य करता है** और एक हाथ से संपादित किए गए पर विफल हो जाता है।
- अपलोड फ़ाइलों के बगल में `datapack.json` ले जाता है, इसलिए कोई भी इस रेपो के बिना सत्यापित कर सकता है:
`pip install mcptoolshop-rnd`।

## एकत्रित प्रयोग रिकॉर्ड

एक उपकरण भंडार अपने स्वयं के पूर्व-पंजीकृत विनिर्देशों और रन रिकॉर्ड (interlock की रसीदें) को कमिट करता है, जिस तरह से प्रत्येक भंडार अपने एटलस मानचित्र को कमिट करता है। लाइब्रेरी केवल संख्याओं की एक ट्रिम की गई प्रति प्रकाशित करती है, जिसे `rnd collect` द्वारा उपकरण भंडार से पिन किए गए कमिट पर बनाया जाता है:

```bash
rnd collect                 # list the experiments that collect records
rnd collect e4b             # read each source with git show, trim it, write experiments/e4b/results/
rnd collect e4b --check     # recompute every output; exit 1 if any differs from the committed file
```

- **`experiments/<name>/collect.json`** उस रिपॉजिटरी का नाम बताता है, और उस क्लोन का भी, जिससे यह डेटा प्राप्त करता है (`--clone` इसे बदल देता है), और प्रत्येक स्रोत का भी: उसका पथ, कमिट, उसके बाइट्स की SHA-256 संख्या, आउटपुट और प्रयोग के `extract.py` में ट्रिम फ़ंक्शन।
- **एक निश्चित स्रोत कभी नहीं बदलता।** वे बाइट्स जिनका हैश अब पिन से मेल नहीं खाता, उन्हें अस्वीकार कर दिया जाता है।
- **प्रत्येक रिकॉर्ड में उत्पत्ति की जानकारी होती है:** रिपॉजिटरी, स्रोत पथ और ट्रिम किए गए बाइट्स की SHA-256 संख्या।
- **प्रत्येक आउटपुट लिखने से पहले सार्वजनिक रूप से सुरक्षित होता है।** कोई भी मशीन पथ, होम डायरेक्टरी या पर्यावरण फ़ील्ड नहीं रहता है, और एक प्रयोग का मॉड्यूल अधिक सख्त सुरक्षा जोड़ सकता है। किसी भी अस्वीकृति पर कुछ भी नहीं लिखा जाता है।

## परीक्षण से पहले किसी उपकरण का परीक्षण करना

`rnd probe <url> …` प्रत्येक स्रोत के अपने एपीआई से किसी उपकरण या मॉडल के बारे में पहले प्रश्न का उत्तर देता है, न कि किसी वेब पेज के सारांश से:

- **GitHub** (`gh api` के माध्यम से, इसलिए यह आपके GitHub CLI लॉगिन का उपयोग करता है): लाइसेंस, क्या यह संग्रहीत है, अंतिम पुश, नवीनतम रिलीज़, और "टेलीमेट्री" के लिए एक कोड खोज। एक हिट पढ़ने के लिए एक संकेत है, कभी भी प्रमाण नहीं; शून्य हिट भी प्रमाण नहीं है।
- **हगिंग फेस:** लाइसेंस टैग, या "अन्य" के लिए कार्ड का लाइसेंस नाम और लिंक; गेटिंग; अंतिम परिवर्तन।
- **PyPI और npm:** लाइसेंस, नवीनतम संस्करण और यह कब प्रकाशित किया गया था।
- **rnd स्वयं:** नाम के लिए एक सटीक-शब्द खोज, ताकि आप जान सकें कि लाइब्रेरी में यह पहले से मौजूद है या नहीं।

एक ऐसे स्रोत को, जिस तक पहुंचा नहीं जा सकता, अज्ञात के रूप में रिपोर्ट किया जाता है, साथ में इसका कारण भी।

```bash
python -m rnd watch --only ollama    # one source
```

जो कुछ भी इसने देखा, उसे रिपॉजिटरी के बाहर एक राज्य फ़ाइल में रखा जाता है (`--state`, अन्यथा `$RND_WATCH_STATE`, अन्यथा `Path.home() / ".rnd" / "watch-state.json"`, `~/.rnd/watch-state.json`) जब तक कि `--no-save` पास न किया जाए। किसी स्रोत की पहली जांच एक आधार रेखा है: यह वर्तमान वस्तुओं को रिकॉर्ड करता है और किसी भी नई वस्तु की रिपोर्ट नहीं करता है। एक प्री-रिलीज़ को कभी भी स्रोत के नवीनतम संस्करण के रूप में रिपोर्ट नहीं किया जाता है; यदि कोई नया प्री-रिलीज़ हो, तो उसे नवीनतम संस्करण के बगल में दिखाया जाता है। GitHub रिलीज़ नोट्स और कमिट संदेश JSON आउटपुट में रखे जाते हैं, ताकि पाठक को प्रत्येक पृष्ठ को प्राप्त करने की आवश्यकता न हो। एक ऐसे स्रोत को, जिस तक पहुंचा नहीं जा सकता, अज्ञात के रूप में रिपोर्ट किया जाता है, और इसकी स्थिति को अपरिवर्तित छोड़ दिया जाता है ताकि चुपचाप कुछ भी छोड़ न दिया जाए।

कमांड एक साप्ताहिक अनुष्ठान का नियतात्मक आधा हिस्सा है (निदेशक, 2026-10-13)। एक स्काउट नई वस्तुओं को पढ़ता है, किसी भी संभावित उपकरण का `rnd probe` के साथ परीक्षण करता है, लाइब्रेरी की `rnd search --exact` के साथ जांच करता है, और एक संक्षिप्त रैंक वाली रिपोर्ट लिखता है: क्या फ़ाइल करना है, क्या प्रयास करना है, और क्या छोड़ना है। पुल अनुरोध द्वारा एक स्रोत जोड़ें, और बताएं कि यह क्यों महत्वपूर्ण है।

## अन्य स्टूडियो उपकरणों से संबंध

- **readouts** वह सत्यापित शेल्फ है जिसे यह बेंच पोषित करता है (ऊपर देखें)।
- **research-os** एक विषय के लिए एक गेटेड, स्थिर प्रमाण पैक बनाता है। एक ऐसा विषय जिस पर निर्णय निर्भर करता है, वह research-os पैक में बदल सकता है, जो प्रविष्टि से जुड़ा होता है।
- **repo-knowledge** स्टूडियो के अपने रिपॉजिटरी को अनुक्रमित करता है; यह लाइब्रेरी उनके बाहर से ज्ञान को कवर करती है।
- कुछ डिज़ाइन करते समय एकत्र की गई जानकारी भी यहां होनी चाहिए, ताकि वे उस सत्र से आगे भी बनी रहें जिसने उन्हें उत्पन्न किया।

पूर्ण उपकरण रजिस्ट्री के लिए `python -m rnd tools` देखें, और स्टूडियो के वर्कफ़्लो मानकों के विरुद्ध वर्कफ़्लो कैसे स्कोर करता है, इसके लिए [docs/standards.md](docs/standards.md) देखें।

## सुरक्षा और विश्वास

- **डेटा लिखा जाता है**, यह इस बात पर निर्भर करता है कि यह कहाँ संग्रहीत होता है:
- **इस रिपॉजिटरी के अंदर** (लाइब्रेरी: `--library`, अन्यथा `$RND_ROOT`, अन्यथा कार्यशील निर्देशिका में या उसके ऊपर निकटतम फ़ोल्डर जिसमें `entries/` और `instruments/` हों, अन्यथा वह रिपॉजिटरी चेकआउट जिससे पैकेज चलता है): `rnd new` (`entries/` या `instruments/` के अंतर्गत एक नई फ़ाइल, कभी भी अधिलेखित नहीं करता), `rnd new-question` (`questions/`), `rnd new-experiment`, `rnd runs record` और `rnd collect <name>` (`experiments/<name>/`), `rnd claims assign`, `rnd reconcile` और `rnd sync` (मौजूदा मार्कडाउन फ़ाइलों में दावों की पंक्तियाँ और बाउंड संख्याएँ), `rnd change` (`changes/`), `rnd bump` (`mcptoolshop_rnd/__init__.py` और `CHANGELOG.md`, प्रत्येक के बगल में अस्थायी फ़ाइलों के माध्यम से, और यह उपयोग किए गए `changes/` अंशों को हटा देता है), `rnd catalog sync` (`catalogs/<name>/catalog.json`), `rnd datapack build` (`datapacks/<name>/datapack.json`) और `rnd layout` (`docs/layout.json`)।
- **इंडेक्स:** `rnd.db`, या `--db` या `$RND_DB` द्वारा दिया गया पथ, इसके निर्माण के दौरान इसके बगल में एक अस्थायी `.db.tmp` फ़ाइल। `rnd build` इसे लिखता है, और प्रत्येक कमांड जो इंडेक्स को पढ़ता है (`search`, `show`, `list`, `tools`, `stats`, `catalog`, `claims`, `questions`, `sql`, `runs`, `ledger`, `where`, `probe`) पहले इसे फिर से बनाता है जब कोई स्रोत फ़ाइल बदल जाती है। मिस लॉग `rnd.misses.jsonl` इसके बगल में होता है (नीचे देखें)।
- **आपका होम फ़ोल्डर:** `rnd watch` अपनी देखी गई वस्तुओं की फ़ाइल को `--state` पर लिखता है, अन्यथा `$RND_WATCH_STATE`, अन्यथा `~/.rnd/watch-state.json` (कोड में `Path.home() / ".rnd" / "watch-state.json"` के रूप में निर्मित), जहाँ यह विभिन्न रन में बना रहता है। यह इसके बगल में एक `.tmp` फ़ाइल के माध्यम से लिखा जाता है। `--no-save` लेखन को छोड़ देता है।
- **इस रिपॉजिटरी के बाहर कच्चे डेटा स्टोर:** `rnd raw ingest`, `rnd raw private` और `rnd raw relicense` सार्वजनिक स्टोर (`--public`, अन्यथा `$RND_DATA`, अन्यथा `../rnd-data`) और निजी स्टोर (`--private`, अन्यथा `$RND_DATA_PRIVATE`, अन्यथा `../rnd-data-private`, लाइब्रेरी के बगल में) में लिखते हैं; जब `rnd raw` को लाइब्रेरी के बाहर चलाया जाता है, तो `rnd-data-private` सार्वजनिक स्टोर के बगल में। `rnd raw ingest` 256 KB से बड़ी प्रत्येक फ़ाइल को ब्लॉब स्टोर में भी रखता है, जो `$RND_DATA_STORE_D` या सार्वजनिक स्टोर के `store.local.json` की `"d"` प्रविष्टि द्वारा नामित फ़ोल्डर में `blobs/` के अंतर्गत होता है (कोई डिफ़ॉल्ट नहीं है; इसके बिना, इनजेस्ट अस्वीकार कर देता है)। ब्लॉब्स को उनके बगल में एक `.tmp` फ़ाइल के माध्यम से लिखा जाता है और केवल-पढ़ने योग्य चिह्नित किया जाता है। `--link` के साथ, एक नया ब्लॉब स्रोत फ़ाइल का एक हार्ड लिंक होता है, इसलिए **वह स्रोत फ़ाइल भी केवल-पढ़ने योग्य हो जाती है** (स्टोर में पहले से मौजूद ब्लॉब को अपरिवर्तित छोड़ दिया जाता है, और उसके स्रोत को भी); `--link` के बिना, स्रोत में कोई बदलाव नहीं होता। `rnd raw ingest --update` नए लिखने से पहले दोनों स्टोर में किसी रन की पिछली छोटी फ़ाइलों को हटा देता है। `--dry-run` कुछ भी नहीं लिखता है।
- **पढ़ता है, कभी नहीं लिखता:** `rnd readouts` (SQLite केवल-पढ़ने योग्य मोड), `rnd collect` स्रोत क्लोन (`git show`), `rnd raw verify`, `rnd datapack verify --copy`, `rnd runs record --from`, `rnd abmine`, और `rnd similar` और `rnd digest`, जो मेमोरी में काम करते हैं और कहीं भी कुछ भी नहीं लिखते हैं: कोई अस्थायी फ़ाइल नहीं, कोई कार्यशील-ट्री नहीं, गिट इंडेक्स या `rnd.db` परिवर्तन नहीं।
- **यह जो कोड चलाता है:** `rnd collect <name>`, `--check` के साथ या उसके बिना, लाइब्रेरी (`mcptoolshop_rnd/collect.py:142-149`) से `experiments/<name>/extract.py` (या उस फ़ोल्डर का `collect.json` जो मॉड्यूल को इंगित करता है) लोड और चलाता है। पायथन उस मॉड्यूल के बाइटकोड को `experiments/<name>/__pycache__/` में कैश कर सकता है। `rnd` स्वयं जो लिखता है उसे केवल `experiments/<name>/` तक सीमित रखता है; यह उस मॉड्यूल के अपने कोड द्वारा किए जाने वाले कार्यों को सीमित नहीं करता है, इसलिए इसे केवल उसी लाइब्रेरी पर चलाएं जिस पर आप भरोसा करते हैं।
- **`rnd` कमांड के बाहर:** पैकेज `mcptoolshop_rnd.localbuilders` को भी शिप करता है, जो स्थानीय-बिल्डरों प्रयोग का ढांचा है। कोई `rnd` कमांड इसे नहीं चलाता है। सीधे चलाए जाने पर (उदाहरण के लिए `python -m mcptoolshop_rnd.localbuilders.runner`), उस किराए की मशीन पर जिसके लिए इसे लिखा गया था और आंशिक रूप से रूट के रूप में, यह कॉलर द्वारा दिए गए पथों (कार्य, होम, इतिहास, वर्चुअल-पर्यावरण, रसीद, लॉग, रिपोर्ट, गुप्त-निर्देशिका और रोकथाम-जांच पथ) के अंतर्गत फ़ाइलें बनाता व हटाता है तथा उनके मालिक और अनुमतियों को बदलता है, और इसका स्कोरर ऑपरेटिंग सिस्टम के अस्थायी फ़ोल्डर में एक अस्थायी फ़ोल्डर का उपयोग करता है, जिसे समाप्त होने पर हटा दिया जाता है।
- **डेटा अपरिवर्तित:** कोई भी `rnd` कमांड अन्यत्र कहीं भी किसी फ़ाइल को नहीं लिखता, नहीं हटाता या नहीं बदलता। यह कोई क्रेडेंशियल संग्रहीत नहीं करता है और न ही पढ़ता है।
- **नेटवर्क:** कोई नहीं, सिवाय `rnd catalog sync`, `rnd probe` और `rnd watch` के, जो सार्वजनिक मेटाडेटा पढ़ते हैं या आपके स्वयं के `gh` CLI लॉगिन के माध्यम से GitHub API को कॉल करते हैं जब आप उन्हें चलाते हैं।
- **अनुमतियाँ:** सामान्य फ़ाइल एक्सेस। किसी भी `rnd` कमांड को उन्नत अधिकारों की आवश्यकता नहीं है, और कोई पृष्ठभूमि सेवा नहीं है।
- **स्थानीय-केवल उपयोग लॉग:** कुछ भी एकत्र या कहीं भी नहीं भेजा जाता है। जब `rnd search` कोई मिलान नहीं लौटाता है, तो यह `rnd.db` के बगल में `rnd.misses.jsonl` में एक पंक्ति (UTC समय और क्वेरी) जोड़ता है (रिपॉजिटरी में गिट-अस्वीकृत; `--db foo.db` के साथ, इसके बगल में `foo.misses.jsonl`, `foo.db.misses.jsonl` नहीं, और इसी तरह `$RND_DB` के लिए)। इसे बंद करने के लिए `RND_NO_USAGE=1` सेट करें, और किसी भी समय `.misses.jsonl` फ़ाइल को हटाकर इसे साफ़ करें। अन्य किसी भी उपयोग डेटा को रिकॉर्ड नहीं किया जाता है।
- **सार्वजनिक रिपॉजिटरी स्वच्छता:** प्रत्येक पुश से पहले, होम-निर्देशिका पथ और ऑपरेटर पहचान के लिए ट्री को स्कैन किया जाता है।
