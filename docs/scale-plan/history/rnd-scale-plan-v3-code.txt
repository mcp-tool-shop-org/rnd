  13  ## Standards compliance (workflow standards, 0–3)
  14
  15  - **PIN_PER_STEP — 2.**
  16    - Every move is made by a script at a pinned rnd commit, and every byte moved carries its SHA-256 in a manifest.
  17    - The datapack format already does this (`rnd-datapack/v1`).
  18  - **ANDON_AUTHORITY — 2.**
  19    - `rnd check` gains the size, layout and private-file rules (§4) and exits 1 on a breach, so CI stops a bad
  20      commit.
  21    - A backup or ingest stops on the first hash mismatch.
  22  - **NAMED_COMPENSATORS — 2.** See §8. Owner: R&D for the rnd side, the Publisher for uploads and repo settings.
  23  - **DECOMPOSE_BY_SECRETS — 2.** Text, small public data, bulk public data, raw data and private data change for
  24    different reasons, and each has its own home.
  25  - **UNCERTAINTY_GATED_HUMANS — 2.** The irreversible steps each wait on the Director's go: a new repository, a public
  26    upload, deleting a local copy. Each is asked contrastively in §9.
  27  - **EXTERNAL_VERIFIER — n/a.** No specialized claims. Argon reviews the design as normal practice.

  71  ## 2. The problems this solves
  72
  73  1. **Single copies on one USB drive.** The sealed gold keys, 20 GB of window receipts and the watch's history.
  74     A fault on E: loses the evidence behind published results. **This is the only problem here that can lose data,
  75     so it's solved first (P0).**
  76  2. **Bulk data in the clone grows without bound.** Every run can add megabytes of verdict JSONL to git, forever.
  77  3. **No map of where bytes live.** Finding a run's raw output means knowing which disk, folder and tar it's in.
  78  4. **No machine-readable record of experiments.** A question like "which runs used Muse at Q8_0, and what did they
  79     cost?" means reading prose READMEs.
  80  5. **Duplicated builds** in the receipts.

  82  ## 3. The design: five tiers, each with one home
  83
  84  Every file belongs to exactly one tier. The tier decides where it lives, how it's backed up, and who may see it.
  85
  86  | Tier | What | Home | Public? | Copies |
  87  |---|---|---|---|---|
  88  | **T1 text** | entries, instruments, designs, results write-ups, briefs, code | rnd git | yes | GitHub |
  89  | **T2 small data** | data a reader needs to check a result: CSVs, trimmed collected records, prereg files, small structured inputs | rnd git | yes | GitHub |
  90  | **T3 bulk data** | processed data a reader may want but rnd needn't carry: verdict dumps, diffs, screens | data packs on Hugging Face, manifest in rnd | private until a publish go | HF + D: |
  91  | **T4 raw** | run outputs from any venue (rig, Colab, RunPod): tars, generations, logs, journals, receipts, custom builds | **new private repo `rnd-data`** (manifests + small files in git), bytes on D: and off-site | never | git (manifests) + D: + off-site |
  92  | **T5 private** | sealed gold keys (held-out keys for blind tests), item text, blind files, private project notes, the watch's history | `rnd-data/private/` in git | never | GitHub (private) + D: |
  93
  94  **The content rule** (round 1 Q1): what a file is decides its tier first, and size second.
  95  - **Per-item raw generations, raw verdict dumps and raw run logs** are T3 or T4, whatever their size.
  96  - **Small structured files** stay in T2 under the size limits: a prompt list, a trimmed collected record, a prereg.
  97  - **"Gold" in a public pack** (for example `data/gold.json`, a published benchmark's labels) is T3 and public. Only
  98    **sealed** gold keys, held out for a blind test, are T5.
  99
 100  **Not stored by us:** model weights already hosted upstream. Their pin and SHA-256 go in the manifest.
 101
 102  **Stored once, by content (round 1 F3):** builds we made ourselves, such as llama-server.
 103  - They live once in `D:/rnd-data/blobs/<sha256>/` and off-site.
 104  - Each window's manifest lists them by SHA-256.
 105  - No window points inside another window's folder, so archiving one window can't break another.
 106
 107  **readouts is unchanged.** It stays the shelf of verified knowledge bases. Its 10.8 GB of generated media is
 108  readouts' own matter, listed here only so nobody puts it in rnd-data by accident.

 110  ## 4. rnd itself: conventions that `rnd check` enforces
 111
 112  **The size rule (T2).**
 113  - A tracked file over 256 KB under `experiments/` fails `rnd check`, unless it's on the grandfather list.
 114  - An experiment over 2 MB in total fails the same way.
 115  - **The grandfather list** is generated once from today's files, so nothing turns red on day one. It may shrink,
 116    never grow, without an R&D review line.
 117
 118  **The private-file rule (round 1 F5).** `rnd check` fails on any tracked file that:
 119  - has a SHA-256 listed in `rnd-data/private/manifest.json`, when a local rnd-data checkout is present;
 120  - or matches the private name patterns below;
 121
 122  - or has a SHA-256 in `private-hashes.txt`, a list of T5 SHA-256s kept in rnd (hashes only, no names or paths),
 123    regenerated whenever `rnd-data/private/` changes. This makes the exact check work in CI, where rnd-data isn't
 124    checked out (round 2 Q3).
 125
 126  **The name patterns,** matching hyphens and underscores alike (round 2 Q3): `*blind*`, `*sealed*`,
 127  `*gold[-_]key*`, `*item[-_]?text*`, `*review[-_]items*`. They're the backstop for a new private file not yet
 128  hashed. A false hit goes on a short, reviewed allow-list.
 129
 130  **The experiment layout** (round 1 F5):
 131  - `README.md`: the design, result and promotion line, as now;
 132  - `experiment.json`: its machine-readable record (below);
 133  - `data/` and `results/`: T2 only (`results/` is where `rnd collect` writes, and `collect.json` stays at the top);
 134  - `scripts/`;
 135  - `staging/`: gitignored, the `--source` for `rnd datapack build`, so bulk files can be built into a pack without
 136    ever being committed.
 137
 138  `rnd new-experiment <name>` scaffolds it from the handbook template.
 139
 140  **`experiment.json`** (schema `rnd-experiment/v1`):
 141  - **Written by people:** name, status (`designing`, `running`, `parked`, `closed`), the design doc, the template
 142    used, budgets, the licences relied on.
 143  - **Written by tools, never typed (round 1 Q5):** the runs.
 144    - The window runner writes `outcome.json` for each run.
 145    - `rnd runs record --from <outcome.json>` adds or updates the run in `experiment.json`: its id, venue, hardware,
 146      date, pins, measured cost, cost unit, projected cost, outcome and raw manifest id.
 147    - It writes no machine paths, the same public-safe rule `rnd collect` already enforces.
 148  - **Budgets:** one per cost unit (`colab_units`, `usd`, `rig_hours`), each with its cap and who set it. Spending is
 149    computed from the runs in that unit, never typed, and never summed across units (round 1 F2).
 150
 151  ## 5. The database
 152
 153  The text stays the source of truth, and the database is rebuilt from it. That's how `rnd.db` works today, and at
 154  thousands of rows a rebuild still takes well under a second.
 155
 156  **`rnd.db` gains six tables:**
 157  - `experiments` (name PK, status, template, design path);
 158  - `runs` (experiment, id, venue, hardware, date, cost, cost_unit, projected_cost, outcome, raw_manifest_id, pins
 159    JSON; PK experiment and id);
 160  - `budgets` (experiment, cost_unit, cap, set_by; spent is computed in the query; PK experiment and cost_unit);
 161  - `files` (sha256 PK, bytes, tier, licence);
 162  - `manifest_files` (manifest_id, path, sha256; PK manifest_id and path): a file's logical path inside a run
 163    manifest or data pack, so `rnd where` finds it by path as well as by hash (round 2 F9);
 164  - `copies` (sha256, store, location; one row per copy).
 165
 166  **Where the rows come from:**
 167  - `experiment.json` files and data-pack manifests, always;
 168  - `rnd-data`'s window and run manifests, when a local rnd-data checkout is present.
 169
 170  **Machine locations stay out of public rnd.** The `copies` rows for D: and off-site come only from rnd-data's
 171  private manifests, never from anything committed to rnd.
 172
 173  **It gains these commands:**
 174  - `rnd runs [--model …] [--venue …]`;
 175  - `rnd ledger <experiment>`: per cost unit;
 176  - `rnd where <sha256 or manifest path>`: every copy.
 177
 178  `rnd sql` already gives read-only SQL. There is one database, not two (round 1 F7).

 180  ## 6. rnd-data, the new repository
 181
 182  - **Name and owner:** `mcp-tool-shop-org/rnd-data`, private.
 183  - **What's in git:**
 184    - `runs/<id>/manifest.json` for every run from any venue. It lists every file's path, SHA-256, size, tier and
 185      licence, and where each copy is. A `models` list at the top gives every generating model with its pin, licence
 186      and required notice, and each raw file inherits from it (round 1 Q6).
 187    - Raw files under 256 KB that matter: logs, journals, receipts JSON, `outcome.json`.
 188    - `private/`: the T5 files and their manifest.
 189    - A README.
 190  - **What's not in git:**
 191    - large raw files, on D: under `D:/rnd-data/runs/<id>/`;
 192    - custom builds, under `D:/rnd-data/blobs/<sha256>/`;
 193    - and the off-site copy of both.
 194  - **The off-site copy:** chosen and filled at P4 (§7) on four criteria, from the vendor's own pages read at the time (round 1
 195    Q3):
 196    - its file-size and total limits: files reach 159 MB, and the total is 20 GB and growing;
 197    - its monthly cost at 20–100 GB, and the egress cost of a full restore;
 198    - whether upload and restore can be checked against the manifest's SHA-256s;
 199    - a scripted restore test.
 200  - **Tooling, in rnd:**
 201    - `rnd raw ingest <dir> --run <id>`: it hashes every file, writes the manifest, places each file on D: and verifies
 202      it by hash, and puts custom builds in the blob store. It never deletes the source.
 203      - **When the source is P0's verified backup on D:,** it hardlinks the files into `D:/rnd-data/` instead of
 204        copying them. D: is NTFS, with 3.37 TB free (measured 2026-10-19), so the 20 GB isn't copied over USB again
 205        (round 2 Q2).
 206      - A hardlink is the same bytes under a second name, not a second copy. D: still counts as one copy in P6's
 207        rule.
 208    - `rnd raw verify --run <id> [--remote]`: it re-hashes every copy, and with `--remote` it restores one run from
 209      off-site into a temporary folder and checks every SHA-256.
 210  - **Per org standards:** the repo-first rule before any coding. rnd-data holds no code, so the Atlas map and the
 211    coverage bar apply only if it ever gains workflows or code.
