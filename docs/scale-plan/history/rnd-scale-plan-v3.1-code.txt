  84  ## 3. The design: five tiers, each with one home
  85
  86  Every file belongs to exactly one tier. The tier decides where it lives, how it's backed up, and who may see it.
  87
  88  | Tier | What | Home | Public? | Copies |
  89  |---|---|---|---|---|
  90  | **T1 text** | entries, instruments, designs, results write-ups, briefs, code | rnd git | yes | GitHub |
  91  | **T2 small data** | data a reader needs to check a result: CSVs, trimmed collected records, prereg files, small structured inputs | rnd git | yes | GitHub |
  92  | **T3 bulk data** | processed data a reader may want but rnd needn't carry: verdict dumps, diffs, screens | data packs on Hugging Face, manifest in rnd | private until a publish go | HF + D: |
  93  | **T4 raw** | run outputs from any venue (rig, Colab, RunPod): tars, generations, logs, journals, receipts, custom builds | **new private repo `rnd-data`** (manifests + small files in git), bytes on D: and off-site | never | git (manifests) + D: + off-site |
  94  | **T5 private** | sealed gold keys (held-out keys for blind tests), item text, blind files, private project notes, the watch's history | `rnd-data/private/` in git | never | GitHub (private) + D: |
  95
  96  **The content rule** (round 1 Q1): what a file is decides its tier first, and size second.
  97  - **Per-item raw generations, raw verdict dumps and raw run logs** are T3 or T4, whatever their size.
  98  - **Small structured files** stay in T2 under the size limits: a prompt list, a trimmed collected record, a prereg.
  99  - **"Gold" in a public pack** (for example `data/gold.json`, a published benchmark's labels) is T3 and public. Only
 100    **sealed** gold keys, held out for a blind test, are T5.
 101
 102  **Not stored by us:** model weights already hosted upstream. Their pin and SHA-256 go in the manifest.
 103
 104  **Stored once, by content (round 1 F3):** builds we made ourselves, such as llama-server.
 105  - They live once in `D:/rnd-data/blobs/<sha256>/` and off-site.
 106  - Each window's manifest lists them by SHA-256.
 107  - No window points inside another window's folder, so archiving one window can't break another.
 108
 109  **readouts is unchanged.** It stays the shelf of verified knowledge bases. Its 10.8 GB of generated media is
 110  readouts' own matter, listed here only so nobody puts it in rnd-data by accident.

 112  ## 4. rnd itself: conventions that `rnd check` enforces
 113
 114  **The size rule (T2).**
 115  - A tracked file over 256 KB under `experiments/` fails `rnd check`, unless it's on the grandfather list.
 116  - An experiment over 2 MB in total fails the same way.
 117  - **The grandfather list** is generated once from today's files, so nothing turns red on day one. It may shrink,
 118    never grow, without an R&D review line.
 119
 120  **The private-file rule (round 1 F5).** `rnd check` fails on any tracked file that:
 121  - has a SHA-256 listed in `rnd-data/private/manifest.json`, when a local rnd-data checkout is present;
 122  - or matches the private name patterns below;
 123
 124  - or carries the private tag `T5-PRIVATE-DO-NOT-PUBLISH`.
 125    - Every T5 text file carries the tag: as a `"tier": "T5-PRIVATE-DO-NOT-PUBLISH"` field in JSON, and as a first-line
 126      comment elsewhere.
 127    - This works in CI, where rnd-data isn't checked out.
 128    - **No list of private files' hashes is published** (round 3 Q2). A sealed key is a short label file, so its raw
 129      SHA-256 could be matched by guessing label sets.
 130  - **The exact SHA-256 check** against `rnd-data/private/manifest.json` runs where rnd-data is checked out: in `rnd
 131    check` on the rig, and in a local pre-push hook.
 132
 133  **The name patterns,** matching hyphens and underscores alike (round 2 Q3): `*blind*`, `*sealed*`,
 134  `*gold[-_]key*`, `*item[-_]?text*`, `*review[-_]items*`. They're the backstop for a file that can't carry the tag (a binary). A false hit goes on a short, reviewed allow-list.
 135
 136  **The experiment layout** (round 1 F5):
 137  - `README.md`: the design, result and promotion line, as now;
 138  - `experiment.json`: its machine-readable record (below);
 139  - `data/` and `results/`: T2 only (`results/` is where `rnd collect` writes, and `collect.json` stays at the top);
 140  - `scripts/`;
 141  - `staging/`: gitignored, the `--source` for `rnd datapack build`, so bulk files can be built into a pack without
 142    ever being committed.
 143
 144  `rnd new-experiment <name>` scaffolds it from the handbook template.
 145
 146  **`experiment.json`** (schema `rnd-experiment/v1`):
 147  - **Written by people:** name, status (`designing`, `running`, `parked`, `closed`), the design doc, the template
 148    used, budgets, the licences relied on.
 149  - **Written by tools, never typed (round 1 Q5):** the runs.
 150    - The window runner writes `outcome.json` for each run.
 151    - `rnd runs record --from <outcome.json>` adds or updates the run in `experiment.json`: its id, venue, hardware,
 152      date, pins, measured cost, cost unit, projected cost, outcome and raw manifest id.
 153    - It writes no machine paths, the same public-safe rule `rnd collect` already enforces.
 154  - **Budgets:** one per cost unit (`colab_units`, `usd`, `rig_hours`), each with its cap and who set it. Spending is
 155    computed from the runs in that unit, never typed, and never summed across units (round 1 F2).

 157  ## 5. The database
 158
 159  The text stays the source of truth, and the database is rebuilt from it. That's how `rnd.db` works today, and at
 160  thousands of rows a rebuild still takes well under a second.
 161
 162  **`rnd.db` gains six tables:**
 163  - `experiments` (name PK, status, template, design path);
 164  - `runs` (experiment, id, venue, hardware, date, cost, cost_unit, projected_cost, outcome, raw_manifest_id, pins
 165    JSON; PK experiment and id);
 166  - `budgets` (experiment, cost_unit, cap, set_by; spent is computed in the query; PK experiment and cost_unit);
 167  - `files` (sha256 PK, bytes, tier, licence);
 168  - `manifest_files` (manifest_id, path, sha256; PK manifest_id and path): a file's logical path inside a run
 169    manifest or data pack, so `rnd where` finds it by path as well as by hash (round 2 F9);
 170  - `copies` (sha256, store, location; one row per copy).
 171
 172  **Where the rows come from:**
 173  - `experiment.json` files and data-pack manifests, always;
 174  - `rnd-data`'s window and run manifests, when a local rnd-data checkout is present.
 175
 176  **Machine locations stay out of public rnd.** The `copies` rows for D: and off-site come only from rnd-data's
 177  private manifests, never from anything committed to rnd.
 178
 179  **It gains these commands:**
 180  - `rnd runs [--model …] [--venue …]`;
 181  - `rnd ledger <experiment>`: per cost unit;
 182  - `rnd where <sha256 or manifest path>`: every copy.
 183
 184  `rnd sql` already gives read-only SQL. There is one database, not two (round 1 F7).

 186  ## 6. rnd-data, the new repository
 187
 188  - **Name and owner:** `mcp-tool-shop-org/rnd-data`, private.
 189  - **What's in git:**
 190    - `runs/<id>/manifest.json` for every run from any venue. It lists every file's path, SHA-256, size, tier and
 191      licence, and where each copy is. A `models` list at the top gives every generating model with its pin, licence
 192      and required notice, and each raw file inherits from it (round 1 Q6).
 193    - Raw files under 256 KB that matter: logs, journals, receipts JSON, `outcome.json`.
 194    - `private/`: the T5 files and their manifest.
 195    - A README.
 196  - **What's not in git:**
 197    - large raw files, on D: under `D:/rnd-data/runs/<id>/`;
 198    - custom builds, under `D:/rnd-data/blobs/<sha256>/`;
 199    - and the off-site copy of both.
 200  - **The off-site copy:** chosen and filled at P4 (§7) on four criteria, from the vendor's own pages read at the time (round 1
 201    Q3):
 202    - its file-size and total limits: files reach 159 MB, and the total is 20 GB and growing;
 203    - its monthly cost at 20–100 GB, and the egress cost of a full restore;
 204    - whether upload and restore can be checked against the manifest's SHA-256s;
 205    - a scripted restore test.
 206  - **Tooling, in rnd:**
 207    - `rnd raw ingest <dir> --run <id>`: it hashes every file, writes the manifest, places each file on D: and verifies
 208      it by hash, and puts custom builds in the blob store. It never deletes the source.
 209      - **When the source is P0's verified backup on D:,** it hardlinks the files into `D:/rnd-data/` instead of
 210        copying them. D: is NTFS, with 3.37 TB free (measured 2026-10-19), so the 20 GB isn't copied over USB again
 211        (round 2 Q2).
 212      - A hardlink is the same bytes under a second name, not a second copy. D: still counts as one copy in P6's
 213        rule.
 214    - `rnd raw verify --run <id> [--remote]`: it re-hashes every copy, and with `--remote` it restores one run from
 215      off-site into a temporary folder and checks every SHA-256.
 216  - **Per org standards:** the repo-first rule before any coding. rnd-data holds no code, so the Atlas map and the
 217    coverage bar apply only if it ever gains workflows or code.
