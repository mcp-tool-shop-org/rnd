### Q1. `google.colab.ai` from outside the Colab UI (before a design depends on it)

Do not depend on `google.colab.ai` for headless CLI pipelines. It is bound to the browser frontend's secret-broker channel unless you drive a browser tab or replicate an undocumented internal RPC.

- **Headless support & why it failed:** `google.colab.ai` is an OpenAI-compatible client wrapper around Google's internal Model Proxy service. On import or first call, it invokes `google.colab.userdata.get('MODEL_PROXY_API_KEY')`, which emits a blocking Jupyter `colab_request` (`GetSecret`) over the kernel WebSocket (`_message.blocking_request('GetSecret', request={'key': key})`). In `google-colab-cli 0.7.4`, `ColabRuntime.colab_request_hook` only intercepts credential propagation for `colab auth` and `colab drivemount` (`/tun/m/credentials-propagation/`). It does not implement a `GetSecret` handler, nor does `colab-mcp` (which is a thin stdio wrapper over `google-colab-cli` that does not use a browser tab). In the VS Code Colab extension, `userdata.get()` similarly times out unless the extension version specifically proxies the secret RPC. (Note: Kaggle's sibling `kaggle-cli` added `kaggle benchmarks auth` in June 2026 to mint short-lived `MODEL_PROXY_API_KEY` tokens locally, so if `google.colab.ai` reads `os.environ` as a fallback or allows client overrides in its source on your VM—check `python -c "import inspect; from google.colab import ai; print(inspect.getsource(ai))"`—you could see how the proxy URL is constructed, though putting a key on the VM violates your no-secrets rule).
- **Models served, rate limits, and compute units:** `ai.list_models()` on paid tiers serves `google/gemini-2.0-flash`, `google/gemini-2.0-flash-lite`, `google/gemini-2.5-flash`, `google/gemini-2.5-flash-lite`, `google/gemini-2.5-pro`, and Gemma 3 (`1b`, `4b`, `12b`, `27b`). Calling `ai.generate_text()` does not charge a per-token fee or deduct extra compute units per call; you only burn the baseline hourly compute units of the VM hosting the notebook (1.07 CU/hr on T4, or ~0.07–0.10 CU/hr on a default CPU runtime). Exact RPM/TPM quotas for the proxy are enforced dynamically per user and are not publicly documented by Google.
- **Least manual way to run a few hundred prompts:** Run them on a CPU-only runtime from a single open browser tab (or Playwright/CDP driving that tab) where the script reads a prompt batch `.jsonl` from `/content/drive`, loops over `ai.generate_text(..., stream=False)` with exponential backoff, writes incremental checkpoints back to Drive, and calls `from google.colab import runtime; runtime.unassign()` in its `finally` block.
- **Confidence:**
  - `colab-cli` and `colab-mcp` lack `GetSecret` interception; `userdata.get` blocks on WebSocket `GetSecret`: checked ([google-colab-cli automation docs](https://github.com/googlecolab/google-colab-cli/blob/main/docs/04_automation_and_utility.md), [colabtools issue #4677](https://github.com/googlecolab/colabtools/issues/4677), [colab-mcp docs](https://mcpservers.org/servers/amgallego8/colab-mcp)).

  - Exact numeric rate limits for `google.colab.ai`: unsure (can't verify exact RPM/TPM numbers; Google does not publish static proxy rate tables).

### Q2. CUDA 13.4 on driver 580 (CUDA 13.0) (before a design depends on it)

Yes, your `cu134` stack and T4 (`sm_75`) are supported on driver 580 without `cuda-compat`, provided your kernels are precompiled SASS (`sm_75`, `sm_80`, `sm_89`) and do not rely on PTX JIT or CUDA 13.4 driver-level features.

- **Minor-version compatibility on driver 580:** NVIDIA's CUDA 13.x family guarantees ABI compatibility across all 13.x toolkits on any R580+ driver (`>= 580.65.06` on Linux; your VM has `580.82.07`). Because both the toolkit (13.4) and the host driver (13.0 / R580) belong to the same major release family, dynamic libraries (`libcudart`, `libcublas`, `libcudnn`, `libcusparse`) work out of the box without installing the `cuda-compat-13-4` forward-compatibility package.
- **What breaks under minor-version compatibility:**
  1. PTX JIT compilation fails: `ptxas` in CUDA 13.4 emits PTX ISA 9.x. The PTX JIT compiler lives inside the host driver (`libcuda.so.580.82.07`), which only understands PTX ISA up to CUDA 13.0. Any library or custom Triton/CUDA extension that falls back to PTX JIT instead of loading precompiled SASS cubins will fail with `CUDA_ERROR_UNSUPPORTED_PTX_VERSION` (222) unless compiled with an explicit `-arch=sm_XX` cubin target (inference assumption derived from NVIDIA's minor-version compatibility architecture).
  2. R615-gated features: Per CUDA 13.4 release notes, new 13.4 hardware platforms and driver-level APIs require an R615+ driver. Standard cuBLAS/cuDNN GEMMs and FlashAttention on T4/L4/A100 do not use these.
  3. Fatbin zstd decompression: CUDA 13.0+ switched fatbin compression from LZ4 to Zstandard (`zstd`), which R580 natively supports.
- **T4 (`sm_75`) support in CUDA 13.x and PyTorch nightlies:** Supported. CUDA 13.0 dropped Maxwell, Pascal, and Volta (`sm_50` through `sm_70`), making Turing (`sm_75`, T4) the minimum supported architecture across all CUDA 13.x toolkits (13.0 through 13.4) and current PyTorch 2.15+ `cu13x` wheels.
- **Confidence:**
  - CUDA 13.4 minor-version compatibility on R580 (`>= 580.65.06`) and R615 requirement for new 13.4 features: checked ([CUDA 13.4 Release Notes](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html), [NVIDIA Minor Version Compatibility Guide](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)).
  - T4 (`sm_75`) support in CUDA 13.x and PyTorch `cu13x`: checked ([PyTorch Dev-Discuss CUDA 12.6 / 13.x notice](https://dev-discuss.pytorch.org/t/notice-cuda-12-6-wheels-will-no-longer-be-published-from-pytorch-2-15-drops-maxwell-pascal-volta/3432), [CUDA Compute Capability Table](https://gpusmith.com/articles/en/cuda-compute-capability-table-gpu)).
  - PTX JIT failure mode (`CUDA_ERROR_UNSUPPORTED_PTX_VERSION`) when PTX version exceeds driver version: likely (standard NVIDIA driver PTX JIT behavior from training recall; unverified specifically against 13.4 PTX on 580.82.07 in this session).

### Q3. Sessions that hang and keep spending (before first use)

Use a three-layer defense: (1) an in-VM Python watchdog thread that calls `runtime.unassign()` (or `os.kill(1, 9)`), (2) an outer host `timeout` wrapping `colab run`, and (3) a post-run verification loop polling `colab sessions` and `colab stop`.

- **Why your `colab exec` hung for 16 minutes:** In `google-colab-cli 0.7.4`, `colab exec` and `colab run` default to a 30-second inactivity timeout (`--timeout 30`), which resets whenever any `iopub` stream traffic arrives (and can still hang if `blocking_request` blocks the kernel shell thread with `timeout_sec=None`, as `userdata.get` does in some paths). Worse, when `colab exec` is used, a failure or client disconnect leaves the remote VM assigned and burning units.
- **Why `colab run` alone is not enough:** `colab run` wraps execution in a `try...finally` block that calls `runtime.stop(shutdown_kernel=True)` and `state.client.unassign(endpoint)`. However, in CLI `0.7.4`, ephemeral cleanup suppresses release errors—meaning a `colab run` exit (or a local `SIGKILL` of the CLI process) is not proof that the backend unassigned the VM.
- **The guaranteed teardown pattern:**
  1. Inside the VM (survives WSL/network death): Start a daemon watchdog thread at the top of every script with a hard wall-clock deadline and an idle-output timer. When triggered—or in the script's top-level `finally:` block—call `from google.colab import runtime; runtime.unassign()`, which tells the Colab backend directly from inside the container to delete the assignment immediately.
  2. On the WSL host: Run `timeout --signal=SIGINT --kill-after=15s <MAX_SEC> colab run --gpu <CARD> script.py` (`SIGINT` lets `colab run`'s `finally` block fire `client.unassign(endpoint)`).
  3. Post-run release verification: Immediately after `colab run` exits, run `colab sessions` (or `colab usage` to check `Active assignments: 0`). If any session remains, explicitly loop `colab stop -s <name>` until `colab sessions` is empty.
- **Spend caps:** There is no native Google Colab setting to cap compute units per session or per day. Colab Pro+ allows continuous execution up to 24 hours and will drain your entire prepaid balance if a session is left running. To enforce a daily/session budget, parse `colab usage` (`Current balance: X compute units, Usage rate: Y/hr`) in your host wrapper script before provisioning and via a background host cron job every 5 minutes.
- **Confidence:**
  - `colab run` teardown mechanics (`client.unassign` in `finally`), `--timeout 30` default, and `colab usage` output format: checked ([05_run_command.md](https://github.com/googlecolab/google-colab-cli/blob/main/docs/05_run_command.md), [02_execution_and_interactive.md](https://github.com/googlecolab/google-colab-cli/blob/main/docs/02_execution_and_interactive.md), [04_automation_and_utility.md](https://github.com/googlecolab/google-colab-cli/blob/main/docs/04_automation_and_utility.md), [Skills Directory CLI 0.7.4 note](https://www.skillsdirectory.com/skills/fmind-colab)).
  - `google.colab.runtime.unassign()` self-termination from inside the kernel: checked ([Stack Overflow / Colab runtime.unassign](https://stackoverflow.com/questions/49554781/how-to-terminate-google-colab-correctly)).
  - Absence of server-side per-session or per-day spend caps in Colab Pro+: checked ([Colab FAQ](https://research.google.com/colaboratory/faq.html)).

### Q4. Getting model weights onto a fresh VM (before first use)

Pull directly from Hugging Face (with `hf_transfer` enabled) or the Ollama registry onto the local `/content` overlay disk. Do not run Ollama's model store directly off `/content/drive`, and do not use Drive as your primary weight cache unless your models are custom-baked and cannot be pulled from a CDN.

- **Speed per compute unit (fastest to slowest):**
  1. Hugging Face Hub / Ollama Registry to local `/content` SSD: Colab VMs sit inside GCP with multi-gigabit egress/ingress to Cloudflare/Fastly/AWS CDNs. Standard `huggingface_hub` downloads hit ~150–300 MB/s per stream, and setting `HF_HUB_ENABLE_HF_TRANSFER=1` (Rust multi-chunk downloader) or `aria2c -x 16` routinely saturates 400–800+ MB/s (pulling a 15 GB model in ~20–35 seconds).
  2. Google Drive (`colab drivemount` / `drivefs`): Slower and subject to hidden double-I/O. `drivefs` is a proprietary FUSE mount (`/opt/google/drive/drive`). Sustained sequential reads of single massive `.gguf` or `.safetensors` files typically plateau around 80–200 MB/s, and `colab drivemount` requires an interactive OAuth/credential-propagation handshake on every fresh VM unless cached.

  (Note: If you have custom studio checkpoints that cannot go on public HF without a token, staging them in a Regional Google Cloud Storage bucket in the same US region as the VM and pulling via `gcloud storage cp` after `colab auth` hits 500–1,000+ MB/s, though `colab auth` links your GCP identity to the VM).
- **Running `OLLAMA_MODELS` directly from `/content/drive`:** Do not do this.
  1. Hidden local disk exhaustion: Whenever a process reads a file on `/content/drive`, `drivefs` transparently stages and caches the entire file into `/root/.config/Google/DriveFS` on the local 236 GB overlay disk. You pay the full network copy time on first read anyway, and the cached blocks stay locked in `/root/.config/Google/DriveFS` as long as `ollama serve` holds the file descriptor open.
  2. `mmap` stalls: `llama.cpp` (Ollama's backend) uses `mmap()` by default to map GGUF weights into virtual memory. Over FUSE (`fuse.drive`), page faults during model load block kernel threads waiting on userspace FUSE reads, causing severe load spikes and occasional timeouts.
- **Known Drive throughput limits:** Google enforces undocumented per-user daily bandwidth and API request quotas on DriveFS. Repeatedly reading 25 GB blobs across dozens of ephemeral `colab run` sessions in a single day can trigger temporary DriveFS 403/rate-limit stalls, and directories with thousands of small files suffer severe FUSE metadata latency.
- **Confidence:**
  - `drivefs` FUSE architecture (`/opt/google/drive/drive`) and `/root/.config/Google/DriveFS` local caching behavior: checked ([colabtools drive.py](https://github.com/googlecolab/colabtools/blob/main/google/colab/drive.py), [Colab Disk vs DriveFS cache](https://stackoverflow.com/questions/60956872/google-colab-disk-space-vs-google-drive-disk-space)).
  - Relative throughput (HF/Ollama CDN vs DriveFS FUSE) and `llama.cpp` `mmap` behavior over FUSE: likely (300 MB/s single-stream HF speed verified in [Colab notebook logs](https://colab.research.google.com/github/unslothai/notebooks/blob/main/nb/Llama3_(8B)-Ollama.ipynb); `hf_transfer` and `mmap` over FUSE behavior from unverified training recall).

### Q5. Pinning the hardware and image (before a design depends on it)

You cannot request an A100 80 GB on Colab Pro+, and you cannot pin the VM image from `google-colab-cli`. You must treat the image as mutable and fail-fast on `COLAB_RELEASE_TAG` drift.

- **A100 40 GB vs 80 GB:** In standard Colab Pro+, `--gpu A100` (`variant=GPU, accelerator=A100`) only provisions the 40 GB SKU (`a2-highgpu-1g`, 40,960 MiB VRAM, 12 vCPUs, ~83.5 GB host RAM). If you need 80 GB of VRAM in `google-colab-cli 0.7.4`, you must request `--gpu H100` (which allocates an 80 GB H100, at a higher CU/hr burn rate), or move to Colab Enterprise / GCP Vertex AI where `a2-ultragpu-1g` (A100 80 GB) is explicitly selectable.
- **How often Colab updates the VM image:** Google updates the public runtime image (`us-docker.pkg.dev/colab-images/public/runtime`) roughly every 2 to 4 weeks (with occasional out-of-band RC builds). Python minor versions and pre-baked packages (`torch`, `transformers`, `jax`) bump with these releases; the host NVIDIA driver (currently `580.82.07`) updates less frequently on the underlying GCE host fleet, independent of the container layer.
- **Pinning vs. detecting the image:**
  - Detecting: Every Colab container exports `os.environ["COLAB_RELEASE_TAG"]` (for example, `release-colab-external_20251217-060051_RC00`). Log `(os.environ.get("COLAB_RELEASE_TAG"), torch.cuda.get_device_name(0), DriverVersion, PythonVersion)` as your canonical machine line at script startup and abort immediately if any field drifts.
  - Pinning: In the browser UI (`Runtime -> Change runtime type -> Runtime Version`), Colab lets you select a past runtime version (kept for 1 year), which takes 2–3 extra minutes on boot because the VM pulls the older ~38 GB Docker image and restarts. However, `google-colab-cli 0.7.4`'s `client.assign` only exposes `--gpu`, `--tpu`, and `--high-mem` (`variant`, `accelerator`, `shape`) and does not expose a flag for `runtime_version`. For strict multi-week reproducibility across image bumps, use `uv venv --python 3.13` with a locked `uv.lock` file inside your job startup (`uv` is pre-installed on the Colab image), or pull the exact digest of `us-docker.pkg.dev/colab-images/public/runtime@sha256:...` when running on your own local/RunPod hardware.
- **Confidence:**
  - `COLAB_RELEASE_TAG` environment variable and `us-docker.pkg.dev/colab-images/public/runtime` registry: checked ([Colab Docker container analysis](https://medium.com/@gogasca_/docker-container-analysis-and-optimizations-629f58073784), [Colab Past Runtime Versions FAQ](https://research.google.com/colaboratory/runtime-version-faq.html)).

### Q6. A Linux GPU-safety governor on a Colab VM (nice to know)

NVML readings (VRAM, utilization, temperature) and cgroup memory limits are reliable inside Colab VMs, and hitting host OOM kills the child process/kernel—leaving the VM alive to run a supervisor or drain script.

- **NVML and cgroup reliability:** Colab VMs are single-tenant GCE virtual machines (`n1-highmem`, `g2-standard-12` for L4, `a2-highgpu-1g` for A100) where the PCIe/SXM GPU is passed through to the VM and exposed to the user container via `--runtime=nvidia`. `pynvml` / `nvidia-smi` queries (`nvmlDeviceGetMemoryInfo`, `nvmlDeviceGetUtilizationRates`, `nvmlDeviceGetPowerUsage`) read directly from the physical card's driver and are accurate. Host RAM limits can be read reliably from `/proc/meminfo` (`MemAvailable`) and `/sys/fs/cgroup/memory.current` + `memory.max` (or `/sys/fs/cgroup/memory/memory.usage_in_bytes` depending on whether the host image uses cgroup v2 or v1).
- **GPU temperature:** Yes, `nvmlDeviceGetTemperature(handle, NVML_TEMPERATURE_GPU)` and `nvidia-smi --query-gpu=temperature.gpu --format=csv,noheader` return real die temperatures in °C on T4, L4, and A100 in Colab. (What you cannot do is change power limits or clocks via `nvidia-smi -pl` or `-lgc`, as those require host-level root capabilities stripped from the container—inference from standard `--runtime=nvidia` container privileges).
- **What happens on host OOM:** The Linux kernel OOM killer inside the container sends `SIGKILL` (`exit code 137` / `-9`) to the process with the highest `oom_score`—which is always your Python worker or `ollama runner` subprocess, not PID 1 of the container. When executed via `colab exec` or a notebook cell, the Jupyter kernel restarts (wiping Python memory state while leaving the VM running and still billing units!). If you run your workload as a subprocess spawned by a light parent supervisor script inside `colab run`, the parent supervisor survives the child's `SIGKILL`, can log the OOM event, flush artifacts, and let `colab run` tear down the VM cleanly.
- **Confidence:**
  - `nvidia-smi` temperature, memory, and utilization availability in Colab: checked ([Saturn Cloud Colab GPU Spec guide](https://saturncloud.io/blog/how-to-get-allocated-gpu-spec-in-google-colab/)).
  - OOM killer targeting the worker/kernel process while leaving the container and billing active: likely (standard Colab Linux container behavior from training recall; unverified via live test on the 2026-10-16 image).

### Q7. Anything else that commonly wastes units or breaks reproducibility on Colab Pro+

1. **Silent hardware downgrade when requesting `--gpu A100` or `L4` (breaks reproducibility & wastes units):** When a regional pool is exhausted, Colab's assignment backend can occasionally fall back or allocate a different shape if not strictly checked, or allocate a default-RAM T4 when `--high-mem` was omitted. Because your T4 measurement had 12.7 GB host RAM (standard shape), pass `--high-mem` on T4 runs (`colab run --gpu T4 --high-mem`) to get ~25–51 GB host RAM at a marginal CU difference—12.7 GB host RAM will OOM during `transformers` shard loading or `gguf` quantization before weights even reach the GPU. Always assert `torch.cuda.get_device_name(0)` in the first 2 seconds of your script and immediately call `runtime.unassign()` if it does not match the target card.
2. **Pre-baked PyTorch / CUDA mismatch (`torch` in `/usr/local/lib` vs your `cu134` nightly):** The Colab container comes with ~38 GB of pre-installed packages in system Python. Installing a `cu134` torch nightly into system site-packages via `pip` often leaves stale `torchvision`, `torchaudio`, or `triton` binaries behind, or triggers `pip`'s dependency resolver to waste 3–5 minutes (0.3–0.45 CU on A100) resolving conflicts. Always install with `uv pip install --system --no-deps` or create an isolated `uv venv` (takes <1 second).
3. **CPU throttling and Xeon generation lottery on T4 (breaks timing benchmarks):** While L4 (`g2-standard-12`, Cascade Lake / Emerald Rapids) and A100 (`a2-highgpu-1g`, Rome/Milan or Cascade Lake) have consistent 12-vCPU shapes, T4 instances are drawn from heterogeneous `n1` pools spanning Skylake, Broadwell, Haswell, and Cascade Lake CPUs with only 2 vCPUs (1 physical core, 2 threads). Any benchmark that measures time-to-first-token (TTFT), tokenization throughput, or CPU-bound prompt preprocessing on a T4 will have high variance unless you record `/proc/cpuinfo` (`model name`) and pin thread counts (`OMP_NUM_THREADS=2`, `MKL_NUM_THREADS=2`).
4. **Outbound network rate-limiting on rapid small requests:** Colab throttles sustained high-frequency outbound HTTP connections after a few hundred rapid requests. If your study downloads datasets consisting of thousands of individual files or makes rapid external telemetry calls, bundle them into a single `.tar.zst` or `.parquet` archive first.
5. **WSL clock skew breaking OAuth token refresh on long queues:** In WSL2 on Windows, host sleep or hypervisor pauses can cause the WSL system clock to drift, or cause `~/.config/colab-cli/token.json` refresh calls to fail mid-batch. Run `colab whoami` (a hidden debugging command in `google-colab-cli 0.7.4` that forces a token refresh via `creds.refresh(Request())` and prints remaining `expires_in` minutes) before kicking off any multi-hour batch.
