# Distillation exercise: a small verifier student on the math ladder

**Status:** draft v1 (2026-10-09), written by R&D at the Director's ask.
- ASPIRE writes each training leg's mechanics; the Publisher reviews the card plan.
- It becomes the pre-registration once the open choices below are filled in and all three sign off. **Nothing
  runs before that, and nothing before tonight's calibration chain and math ladder v1 have finished.**

## Why this exercise

It does two jobs.
- **A teaching run** for the Director: every step of distillation on a problem whose answers are exact, so
  every result can be trusted and the before/after curves show what training changed.
- **The smoke gate** for the real job: distilling a big model into an 8B verifier for offrig
  (memory: verifier-distillation-direction).
  - Any bug in the pipeline (training, merging, quantizing, `ollama create`, serving, scoring) shows up here,
    where the right answer is known. It doesn't show up on the verifier, where it would look like a model
    weakness.

## The question

Does training a 1.7B model on verified worked examples move its falloff point on the math ladder? By how much,
on which knobs, and how much of the gain survives when the examples come from an imperfect teacher instead of
a perfect oracle?

## Design: three arms, three seeds

| Arm | Trained on | What it teaches us |
|---|---|---|
| **A base** | nothing: the base model through our own packaging | the "before" curve |
| **B-full oracle** | worked answers generated by the ladder itself (exact intermediate values, then the verdict), on all ~2,000 items | the best case: what the student can learn from flawless examples |
| **B-matched oracle** | the same oracle answers, on **exactly the items C kept** (ASPIRE's addition) | holds item difficulty and count equal, so B-matched minus C isolates the quality of the teacher's reasoning |
| **C teacher** | a teacher model's own reasoning traces, **kept only where its final answer is exactly right** (ASPIRE's filter) | real distillation; the gap from B is the cost of an imperfect teacher |

B-full, B-matched and C each train three times, with seeds 42, 43 and 44, and every effect is read against the spread between
seeds. ASPIRE's own fine-tuning experiment once saw a 0.18 seed spread, so a one-seed "it improved" is ruled
out in advance.

## Data

- **Training items:** about 2,000 fresh ladder claims from `math-ladder/generate.py` with a **new seed**
  (proposed 70010), balanced across every cell, supported and unsupported.
- **No overlap with either test set:** a training item is dropped if its function source matches any item in
  ladder v1 or v2 (by a hash of the normalised source).
- **Arm B targets:** offrig's reasoning-first JSON contract.
  - `reasoning`: the exact trace, e.g. "v starts at 16; v - 19 = -3; f returns -3; the claim says -33";
  - `verdict`: supported or unsupported;
  - the evidence quote, as offrig's schema asks.
- **Arm C targets:** the teacher's reasoning and verdict on the same items, in the same contract.
  - Kept only when its verdict matches the truth exactly.
  - The plan reports the drop count and the teacher's abstain rate before training. If the teacher abstains
    often, arm C is starved; that gets reported, not hidden.
- **The test, ladder v2, sealed:** a new seed, plus knob combinations ladder v1 never tested together (for
  example integer traps × loops × units).
  - At least 30 claims per cell; built with the same exact-truth check.
  - **Only its sha256 and counts are committed** before training. The file stays out of every working
    directory until the final scoring.

## Training (written by ASPIRE, 2026-10-09)

### Settings, fixed now

| Setting | Value | Why |
|---|---|---|
| Student | Qwen3-1.7B (HF), revision pinned at plan time | as above |
| LoRA | r=16, α=32, dropout 0.05 on q/k/v/o, **bf16** (`--no-4bit`) | the merged weights are what was trained |
| Epochs | **2**, and **only the final epoch is scored** | the epoch-1 adapter is kept but never read on ladder v2, so there's no picking the best epoch |
| Learning rate | 2e-4, cosine, 5% warmup (sft.py's schedule) | the LoRA standard for this size |
| Batch | 8, no accumulation | ~250 steps per epoch on 2,000 items |
| Max length | **1,024 tokens. An item longer than that is dropped and counted, never truncated** | sft.py truncates from the left, which could cut the claim out of a prompt (a code change below) |
| Seeds | 42, 43, 44 | each seed sets LoRA init and data order (`torch.manual_seed` + `random.seed`); recorded per run |
| Selection | none: no validation-based stopping, no hyperparameter search | every choice is fixed here, before data exists |

**Stop rule on length:** if more than 1% of an arm's items exceed 1,024 tokens, training doesn't start. The
length distribution is reported, and the limit is changed by an amendment, not on the spot.

### Thinking mode and template: a known trap, fixed in code

The student is trained and served with thinking **off**. The reasoning lives in the contract's `reasoning`
field, not in a thinking channel. Qwen3's template with thinking off puts an empty think block,
`<think>\n\n</think>\n\n`, **in the prompt**.
- sft.py today renders without `enable_thinking`. Qwen3 then renders the assistant turn with that empty block
  inside the labelled span, so the model would learn to generate the block that Ollama will already have put
  in the prompt.
- **Change:** sft.py takes `--chat-template-kwargs '{"enable_thinking": false}'`. It passes them to every
  render, so the label span starts after the empty block.
- **Template test (a stop condition):** for 20 fixed items, the prompt Ollama renders for the packaged model
  (the prompt logged by a separate test Ollama instance run with `OLLAMA_DEBUG=1`, never the shared server on
  11434) must equal, **byte for byte**, the training render up to the generation point. Any difference stops
  scoring.
- **Arm C's targets:** the teacher's **contract output only** (its `reasoning` and `verdict` JSON). The
  teacher's hidden thinking is never used, so B and C train on the same format.

### Code changes before anything trains (one aspire-si PR, R&D reviews)

1. `--chat-template-kwargs` passed to every chat render.
2. `--max-length` drops too-long items and reports the count, instead of truncating.
3. Gradient checkpointing for the bf16 path. The 1.7B doesn't need it, but the 8B leg does, and it's tested
   here first.
4. A ledger row per run in `runs.jsonl`:
   - arm, seed, student revision;
   - item count and dropped count;
   - steps, loss per epoch, wall time, peak VRAM;
   - adapter sha256, merged-weights sha256, GGUF sha256, Ollama model digest.
5. Tests for 1–4.

aspire-cu134 already has torch 2.16.0.dev20261008+cu134, transformers 5.19.0, peft 0.21.2 and accelerate

reported, not silent.

### Packaging

1. **Merge:** the final-epoch adapter into a bf16 copy of the pinned student.
2. **Convert:** `convert_hf_to_gguf.py --outtype bf16` from the **same llama.cpp commit as our 13.4 build**,
   with its own `gguf-py`. The commit is recorded.
3. **Quantize:** `llama-quantize` to **Q8_0**, from that build.
4. **Register:** with Ollama's HTTP API, not the CLI: upload the blob with `/api/blobs`, then `/api/create`
   with the Modelfile. Every model is named `distill-ladder-<arm>-s<seed>`.
   - The Modelfile's `TEMPLATE` is Qwen3's chat template. The template test above checks it.
   - Its parameters (temperature, seed, `num_ctx`) are the calibrate run's settings.
5. Arm A goes through steps 2–4 from the untrained base, so A differs from B and C only by training.
6. Undo: delete each model with `/api/delete` and the local files.

### Quant-drift check (a stop condition, before any scoring)

- **Sample:** 200 fresh ladder items from a seed of their own (**70011**), outside training and both test
  sets.
- **Method:** each model answers them twice, greedy (temperature 0):
  - as merged bf16 weights through transformers;
  - as the Q8_0 GGUF through Ollama.
  The prompt is the same, rendered by the template test's path.
- **Measure:** verdict agreement between the two, and the GGUF side's rate of unparsed JSON.
- **Stop if, for any model:**
  - agreement is below 0.95, or the lower bound of its Wilson 95% interval is below 0.90;
  - or the GGUF's unparsed rate is above 1%;
  - or a trained model's agreement is more than 0.03 below arm A's (A's agreement is the floor the pipeline
    itself causes).
- A stop is reported with its numbers. Nothing is re-quantized at another level to get past it without an
  amendment.

### What ASPIRE hands to R&D for scoring

The 10 Ollama model names (A, B-full ×3, B-matched ×3, C ×3), with the ledger, the template test and the
quant-drift readout. Scoring and reading are R&D's.

## Measurement

Every arm and seed is scored the same way: `offrig verify calibrate` with each arm's settings, then
`math-ladder/report.py`. Each run gets its own scratch store.

1. **Ladder v2 (sealed): the headline.** Per-cell accuracy, false accepts and abstains, with Wilson
   intervals, and the falloff cell along the combined ladder and along each knob.
2. **Ladder v1: in-distribution check.** The students trained on ladder-style items, so v1 is reported as
   in-distribution, never as the result.
3. **Transfer: the gold tune split** (grounded and reasoning). Did math training help, hurt, or leave
   general verification alone? The gold held-out split is **not touched**.

## Pre-registered reading (to be fixed when the open choices are filled in)

- **B works:** mean ladder v2 accuracy of B-full minus A ≥ 0.10, all three seeds improve, and the gain is more than
  twice the seed spread.
- **C works:** the same test for C minus A.
- **The cost of the imperfect teacher (primary):** B-matched minus C, with item difficulty and count held
  equal. B-full minus C is reported beside it, along with C's kept items per cell, so a skew toward easy
  cells is visible.
- **Falloff:** the median falloff cell over the seeds, per arm, along the ladder and per knob.
- **False accepts must not rise:** if a trained arm's false-accept rate on ladder v2 rises against A by more
  than its interval, that arm fails whatever its accuracy, because a verifier that accepts more wrong claims
  is worse.
- **Transfer:** descriptive only. A drop of more than 0.05 balanced accuracy on gold tune is flagged as
  "math training hurts general verification".

## What the Director will see, step by step

1. **The "before" curve (arm A):** where a 1.7B model falls off on its own.
2. **The training data:** for arm C, how many of the teacher's traces survive the exactness filter. That's
   the first view of teacher quality.
3. **The "after" curves:** B and C against A, cell by cell. The falloff point moves right if distillation
   worked.
4. **The cost of the teacher:** how much of B's gain C keeps.
5. **Transfer:** whether a model trained on math checks claims about code better, worse, or the same.
